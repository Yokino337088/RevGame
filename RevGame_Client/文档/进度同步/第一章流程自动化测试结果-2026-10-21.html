REPORT / 03

代码放在Animation，按职责细分

保留用户指定的 Assets/GameScripts/Animation 路径，新增Contracts、Input、Flow、Diagnostics、Fixtures子目录。使用现有Revolution门面和现有自动化客户端，没有修改框架快照。

文件 / 模块职责与关键设计
Contracts / GameAutomationPlan可序列化计划、强化、步骤和证据；操作及数值边界在执行前校验。
Input / GamePointerInput按真实控件坐标执行RaycastAll，只接受最上层命中；分帧按下/松开，不直接Invoke按钮或落子服务。
Flow / GameAutomationRunnerRevServices常驻服务，Unscaled RevTimer分帧推进；逐张检查手牌、额度、占格及棋种；观察真实战斗事件。
Diagnostics / GameAutomationCommands六个开发态GM入口；开始、状态、检查、报告、取消、收尾。失败立即返回原始原因。
Fixtures / BattleService.Automation原BattleService的partial开发片段；临时强化租约接入真实攻速、攻击伤害和统一受伤出口。
GameBootstrap与战斗钩子开发态注册/注销执行器；三处小钩子启用强化，正式发行构建不包含它们。
Tests / BusinessFlowAutomationrun_flow.py复用Revolution.Automation；first-chapter.json是可改业务计划；README说明复现与自定义步骤。

核心方法、契约、字段和重要算法步骤已加中文说明。每个执行器只清理自己的owner：指针、计时器、事件与强化租约成对回收。完整源码对应的SHA-256保存在附件，基线提交为3115628。

REPORT / 04

Boss零次攻击仍可合法获胜

本游戏的原有规则是：Boss主将死亡或被锁死即判玩家胜利。六张牌持续积累后，后期棋盘被围得很密，主将可能在第一仿真小步就失去全部气，不需要先发生一次攻击。

最终运行开战时确有9颗敌棋，主将编号129；0.3125模拟秒后，真实BattleEnded给出玩家胜利，执行器确认同一主将满足死亡/锁死条件，记录kingCaptured=true。测试没有主动杀Boss或重写胜负。
