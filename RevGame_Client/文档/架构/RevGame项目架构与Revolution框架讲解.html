    GUIDE / 01

    先把词弄懂

    这个项目的代码量不大，但“词”很多。先用三句话记住全貌，后面所有章节都是在展开它们：

    1. 规则和数据住在“纯 C# 世界”。落子是否合法、谁掉血、谁赢、发什么奖励，全部在 Services / Battle / Board / Pieces / Data / Core 里算。这些目录不引用 UnityEngine，所以连 Unity 都不用开，也能用 dotnet 跑回归测试。
    2. 界面和画面住在“Unity 世界”。Bootstrap / Flow / UI / View 引用 UnityEngine。它们只做两件事：把玩家操作转发给规则，把规则发出的事件画出来。
    3. 两个世界之间只有两座桥。向下是“调用”：界面经 BattleLogic 调 IBattleService；向上是“广播”：规则用 RevEvent 发事件，界面自己订阅。规则永远不会反过来调用界面。
    名词一句话解释本项目里的例子
    服务 Service有状态、全局唯一的业务对象；调用方只认接口，不认具体类型。IBattleService → BattleService
    域 Scope / Domain一段有头有尾的生命周期。进入时启动，退出时把里面的计时器、监听、界面一次收干净。GameDomain.Lobby、GameDomain.Battle
    Logic绑定在某个域上的业务编排类，域关闭它自动停止。BattleLogic（战斗域）
    事件 Event广播“某件事发生了”，发送者不关心谁在听。Events.PiecePlaced、Events.PieceDied
    状态机 FSM同一时刻只处在一个状态，切换路径明确。轻量版管流程，重量版管 AI。GameFlow（轻量）、EnemyAI（重量）
    对象池把用完的对象放回池里复用，代替反复 new / Destroy。棋子 PieceView、弹幕 BattleEffectView
    导表把 Excel 转成游戏能读取的数据表和强类型 C# 类。13 张表 → Generated/BattleDataTables.cs
    Presentation“接线员”：监听阶段事件，决定打开或关闭哪些界面、显示哪个根节点。BattlePresentation、GamePresentation
    固定步长不管手机帧率是 30 还是 60，战斗都按固定的小时间片推进，结果可复现。Balance.BattleSimulationStepSeconds
    读代码的捷径看到 Rev 开头的名字（RevEvent、RevUI、RevServices 等），说明这里在使用 Revolution 框架。看到 RevGame. 开头的命名空间，才是本项目自己的业务。
    GUIDE / 02

    整体架构与目录

    下图按“能不能引用 UnityEngine”把代码分成两个世界。上面的世界可以调用下面的世界，下面的世界永远不会反过来依赖上面——这是整套架构最重要的一条边界，且有证据：Tests/CombatAttackRegression 只把下面那个世界的源文件链接进纯 .NET 控制台程序，就能完整编译并跑通回归。

    Unity 世界 · 引用 UnityEngineBootstrap / Flow / UI / View

    Bootstrap启动层

    场景里唯一的启动宿主 GameBootstrap：初始化框架、注册服务、启动流程；GameGmCommands 注册调试指令。

    Flow流程层

    GameFlow（屏幕状态机 + 场景切换）、SceneResourceWarmup（资源预热）、BattleLogic（战斗域的节奏与入口）。它决定“现在处在哪个屏幕，战斗域开不开”。

    UI界面层

    7 个 RevUIPanel 面板（主页、选关、加载、准备、HUD、结算、奖励）、手牌 CardItem、布局适配。只读服务状态，操作转发给 BattleLogic。

    View表现层

    棋盘 BoardView、棋子 PieceView、弹幕特效、音频、图集服务，以及两个接线员 GamePresentation / BattlePresentation。只订阅事件并播放动画，不二次结算。

    ↓ 调用（向下）界面 → BattleLogic → IBattleService。入口方法统一、失败带原因（LastError）。
    ↑ 广播（向上）BattleService → RevEvent.DispatchEvent → 界面与表现订阅。规则不持有任何 UI 引用。
    纯 C# 世界 · 不引用 UnityEngine可离线 dotnet 回归

    Services服务层

    IBattleService 契约与 BattleService 实现（拆成 14 个文件）：回合、落牌、伤害、胜负、奖励、事件、敌方增援。规则的唯一入口和唯一数据源。

    Battle · Board · Pieces玩法规则

    MoveRules（走法与攻击范围）、GoRules（围棋的气与眼）、BoardModel（9×9 占格）、Piece、HandModel（手牌）、EnemyAI 等（敌方状态机）。

    Data · Generated数据层

    Balance、GameConfig、PieceCatalog、LevelCatalog 等，把 Excel 导出的表整理成强类型、带校验的只读数据。

    Core基础定义

    Events（事件名常量）、Enums、Consts、BoardPos、GameDomain。所有层都能用，它自己谁也不依赖。

    Flow 与 View 的关系要说实话Flow 是“编排者”：GameFlow 会找到场景里的 GamePresentation、打开 LoadingPanel；而界面和棋盘又会通过 RevLogic.Get<BattleLogic>() 调用 Flow。所以 Unity 世界内部并不是严格的单向分层，真正严格的是两个世界之间的边界。

    GUIDE / 03

    从启动到进入战斗

    理解启动顺序，你就理解了框架各模块是怎么被“接上电”的。下面每一步都能在代码里找到对应位置。

    1. GameBootstrap.AwakeBootstrap/Startup/GameBootstrap.cs执行顺序 -100（比其他脚本早），DontDestroyOnLoad 常驻。设置 RevUISetting（横屏、参考分辨率 1920×1080），调用 RevInitialize.Initialize() 一次性初始化框架；随后注册三个服务：GameSpriteAtlasService、IBattleService → BattleService、GameFlow。同时初始化 DOTween（动画库，不属于 Revolution）。仅在 Editor / Development 构建下调用 GameGmCommands.Register() 注册调试指令，正式包里没有这些入口。
    2. GameBootstrap.StartBootstrapawait RevTask.Yield() 等一帧，让场景里的表现脚本先订阅 ScreenChanged，避免表已缓存时同步完成而漏掉首页事件；然后 await GameFlow.StartAsync()。
    3. GameFlow.SwitchSceneAsync(Home)Flow/States/GameFlow.Scenes.cs这是所有“切场景”的统一流程：打开 LoadingPanel 全屏遮挡 → RevScope.Detach 让遮挡面板不被旧域带走 → 首次启动加载全部 Excel 表并整体校验 → 预载图集 → SceneResourceWarmup 预热资源 → RevScene.LoadAsync 加载 StartScene。
    4. Change(target)：交割Flow/States/GameFlow.cs_fsm.ChangeTo(state) 触发 FlowState.OnEnter：RevScope.Enter(域名) 打开对应的域；若目标是战斗，还会调用 BeginCampaign(章节) 生成首回合，再 RevLogic.Start<BattleLogic>() 启动战斗域逻辑。交割之后才广播 Events.ScreenChanged。
    5. GamePresentation.OnScreenView/Scene/GamePresentation.cs收到 ScreenChanged：战斗屏显示棋盘根节点；大厅屏用 RevUI.OpenAsync<HomePanel>() 打开面板。
    6. WaitUntilReadyAsync：可见性屏障等待 81 个格子、开局棋子、HUD、6 张手牌都装配完，才允许遮挡淡出。装配失败会抛出明确原因，不会拿 100% 进度条掩盖缺失的画面。
    7. BattlePresentation 接管界面View/Combat/BattlePresentation.cs棋盘显示后它的 OnEnable 开始订阅 PhaseEnterPrepare / Battle / Settle / Reward，据此打开或关闭 PreparePanel、SettlePanel、RewardPanel，并常驻 BattleHudPanel。
    为什么这么折腾？先确认资源与画面都就绪、再撤遮挡，是为了不让玩家看到白块与半成品界面；IsTransitioning 与 IsGameplayBlocked 则保证加载期间不消耗“准备三秒”、不触发重复进入。

    GUIDE / 05

    服务：用 RevServices 替代单例

    很多项目会写 BattleManager.Instance。这里不这样做，而是“接口 + 服务定位器”：

    // 只在 GameBootstrap.Awake 注册一次（懒创建：第一次取用才 new）
RevServices.Register<IBattleService, BattleService>(owner: this);

// 任何地方使用：只认接口，拿不到会抛出带原因的异常，而不是返回 null
IBattleService battle = RevServices.GetRequired<IBattleService>();
    传统单例本项目的服务
    调用方依赖具体类 Xxx.Instance接口 IBattleService
    谁创建实例类自己 static 创建启动入口统一注册，框架管理
    换实现 / 测试要改所有调用点只改注册那一行；离线测试直接 new 一个带固定种子的实例
    漏初始化得到 null 或悄悄新建GetRequired 当场抛出中文原因
    回收自己写 OnDestroyRevServices.UnregisterAllOf(owner) 一次收干净

    BattleService 为什么拆成 14 个文件

    它是一个类（partial），一个实例，只是按职责拆文件，每个文件只回答一个问题：

    文件它回答的问题
    Contracts/IBattleService对外能做什么、能看什么（契约）
    Simulation/BattleService回合怎么开始、每一小步怎么推进、怎么判胜负
    Preparation/Placement · HandRefresh · Preparation准备期：落牌/换位、刷新手牌、三秒后发放准备增益
    Progression/BattleService.Progression章节进度、奖励三选一、眼位石、跳过回合
    Support/Events · Reinforcement战斗增益事件、统一扣血出口 DamagePiece、援军落点
    AI/EnemyAI · EnemyDeployment敌方状态机的宿主与生命周期、战斗中的敌方增援提交
    Diagnostics/* (4 个)只在 Editor / 开发构建里编译的验收造局
    服务层的三条规矩① 外部只依赖接口；② 每个会失败的方法都返回 false 并写 LastError（中文原因），不能静默失败；③ 只广播事实，绝不 using 任何 UI / View / Flow 命名空间。
    GUIDE / 06

    流程、域与 Logic

    GameFlow：屏幕状态机

    GameFlow 有四个屏幕状态 GameScreen.Home / LevelSelect / Battle / Exit，内部用 RevLightFSM 管理，每个屏幕一个 FlowState。按钮只能调用它提供的入口：OpenLevels()、EnterBattle(章节)、ReturnHome()。过场期间（IsTransitioning）这些入口会拒绝重复触发，并写 LastError。

    域：一局的生命周期

    进入屏幕时 FlowState.OnEnter 调用 RevScope.Enter(GameDomain.Battle) 开启一个域；退出时 RevScope.Exit(句柄)。域关闭时框架会停止域内的 Logic、关闭域内打开的面板，你不需要在每个地方手写“清理上一局”。过场遮挡 LoadingPanel 则用 RevScope.Detach 脱离旧域，由流程自己管理。

    BattleLogic：战斗域的节奏与入口（节选并简化）

    [RevLogic(GameDomain.Battle)]            // 绑定到战斗域：域开它启动，域关它停止
public sealed class BattleLogic : RevLogicBase
{
    protected override void OnStart()
    {
        // 固定步长：不管帧率，每 BattleSimulationStepSeconds 秒推进一小步
        Every(Balance.BattleSimulationStepSeconds, OnFixedTick);
    }
    private void OnFixedTick()
    {
        if (flow.IsGameplayBlocked) { return; }          // 过场遮挡期间不消耗准备/战斗时间
        Battle.Tick(Balance.BattleSimulationStepSeconds); // 交给服务推进
    }
    public bool PlayCard(...)  { return Battle.TryPlayCard(...); }  // 玩家/GM 的统一入口
    public bool ClickBoard(BoardPos pos) { return Battle.HandleBoardClick(pos); }
    protected override void OnStop() { /* 停掉敌方状态机 */ }
}

    它只做两件事：固定节奏（用 RevTimer 的 Every 驱动 Tick）和统一入口（BeginBattle / RefreshHand / SelectCard / PlayCard / ClickBoard / ContinueToNextRound / ChooseReward / SkipRound / SelectEyeStone）。

    为什么按钮不直接调服务？玩家点按钮和 GM 指令走的是同一个 BattleLogic 入口。所以用 GM 测出来的结果，和真实玩家点出来的结果是同一条代码路径，不会出现“GM 能过、手点不能过”。
    GUIDE / 07

    事件：模块之间怎么通话

    项目里一共有三种通信方式，用途不同：

    方式方向什么时候用例子
    调用 Logic界面 → 规则玩家做了一个操作RevLogic.Get<BattleLogic>().PlayCard(...)
    读服务状态界面 ← 规则需要“现在是什么样”battle.Phase、battle.Hand、battle.CardsRemaining
    订阅事件界面 ← 规则需要知道“刚刚发生了什么”RevEvent.AddEventListener(Events.PiecePlaced, ...)

    事件名全部集中在 Core/Events/Events.cs，都是 const string。规则层发事件，界面层订阅；规则永远不知道谁在听。

    // 发送（BattleService 内部）：只发“事实”
RevEvent.DispatchEvent<int>(Events.PiecePlaced, piece.Id);

// 订阅（BattlePresentation.OnEnable）：必须带 owner
RevEvent.AddEventListener<int>(Events.PhaseEnterBattle, OnBattle, owner: this);
// 退订（OnDisable）：按 owner 一次移除，不会漏
RevEvent.RemoveAllByOwner(this);
    订阅必须有主人每次 AddEventListener 都带上 owner，并在对象销毁 / 关闭时 RemoveAllByOwner。无主订阅会让旧对象在下一局继续收事件——这是最典型的泄漏。

    事件目录（核心部分）

    事件谁发谁听
    ScreenChanged(屏幕)GameFlow.ChangeGamePresentation（开/关面板与棋盘）、GameAudio（背景乐）、GameSpriteAtlasService（图集租约）
    PhaseEnterPrepare / Battle / Settle / RewardBattleServiceBattlePresentation（开关面板）、BoardView、PreparePanel、BattleHudPanel；Settle 另有 GameAudio（胜负音）
    PiecePlaced(棋子Id)BattleService（玩家落牌、援军、敌方增援）BoardView（创建 PieceView）、GameAudio（落子音）、BattleHudPanel
    PieceMoved / PieceHpChanged / PieceDiedBattleServiceBoardView（位置、血条、死亡动画）
    PieceAttacked(攻击信息)BattleService.AttackBoardView（出手动画与弹幕）

    三条完整链路

    把前面的概念串起来。每条链路都对应真实代码，你可以按步骤逐个文件对照阅读。

    链路 A：玩家落一张牌

    1. 选牌、点格子PreparePanel / CardItem → BoardView选牌调用 BattleLogic.SelectCard(id)（只改“选择”，不扣牌）；点格子时 BoardCellView 把点击交给 BoardView。
    2. 统一入口View/Board/BoardView.cs → Flow/Logic/BattleLogic.csBoardView 先检查 GameFlow.IsGameplayBlocked（过场中不接受操作）；若正显示攻击范围，这次点击只负责收起；否则调 BattleLogic.ClickBoard(pos)。界面到此为止，不接触任何数据。
    3. 服务判定Services/…/BattleService.Placement.csHandleBoardClick(pos) 的判断顺序是：① 点到己方棋子 → 选中 / 取消选中；点到敌棋 → 拒绝；② 点空格且已选中棋子 → 换位（BoardModel.Move，放不下则拒绝）；③ 战斗期没选棋子 → 拒绝；④ 准备期 → 补眼模式调 TryPlaceEyeStone，否则调 TryPlayCard → PlaceCard：校验阶段、落子额度、整块空间，再 Place 占格、检查三合一升级、继承准备增益、刷新气眼。
    4. 失败也有交代任何一步不合法，服务写 LastError 并发 SelectionChanged，棋子/手牌/额度保持原样，界面直接显示原因。
    5. 广播事实RevEvent成功则发 PiecePlaced、HandChanged、SelectionChanged（及 GoStateRefreshed）。服务到这里就结束了。
    6. 各自反应BoardView 从 RevPool 取出 PieceView 并 Bind；GameAudio 播放落子音；PreparePanel 刷新手牌与剩余额度。它们互不认识，也不需要。

    链路 B：战斗中的一小步

    1. 固定节奏BattleLogic.OnFixedTickRevTimer 每个固定步长触发一次；若流程处于过场则直接返回；否则 Battle.Tick(step)。
    2. 攒时间、切小步BattleService.Tick准备阶段只推进“增益发放”计时；战斗阶段把传入的时间攒进累加器，攒够一个固定小步就循环处理：ResolveOneStep → 敌方增援检查 → 准备增益的战斗效果 → 自动战斗事件 → 通关辅助 → 判断是否结束。帧率再高也不会多算。
    3. 先我方，后敌方ResolveOneStepRefreshGoState → StepSide(Player) → RefreshGoState → StepSide(Enemy)。固定顺序保证相同输入得到相同结果。
    4. 敌方由状态机决定StepEnemyAI → EnemyAI.Tick每颗敌棋的 RevHeavyFSM 在自己的 OnUpdate 里感知（死亡 / 零气 / 有射界 / 移动冷却），切换到 Attack 或 Advance，再执行；执行时只能通过 IEnemyAIOwner 调用服务的原子动作。
    5. 统一扣血出口Attack → DamagePiece先发 PieceAttacked（供动画），再由 DamagePiece 结算伤害（锁死倍伤、护盾、减伤等），发 BattleHit、PieceHpChanged、DamageResolved；死亡则发 PieceDied 并把该敌棋的状态机切到 Dead。伤害只在这里算一次。
    6. 判胜负EndBattle擒王、一方全灭或超时后：停掉敌方状态机，进入 Settle 阶段，发 PhaseEnterSettle，BattlePresentation 据此打开结算面板。

    链路 C：从选关进入战斗

    1. 点击章节LevelSelectPanel → GameFlow.EnterBattle(chapter)检查未过场、处于选关屏、章节已解锁，通过则置 IsTransitioning 并开始异步切换。
    2. 过场与预热GameFlow.SwitchSceneAsync打开 LoadingPanel → 预载战斗图集 → 资源预热 → RevScene.LoadAsync(GameScene) → 预热对象池。
    3. 交割FlowState.OnEnterRevScope.Enter(Battle 域) → BeginCampaign(章节) 生成首回合 → RevLogic.Start<BattleLogic>()。
    4. 画面跟上ScreenChanged → GamePresentation 显示棋盘；BoardView 用对象池创建 81 个格子与开局棋子；BattlePresentation 打开 HUD 与准备面板。
    5. 可见性屏障WaitUntilReadyAsync格子、棋子、HUD、6 张手牌全部就绪才撤遮挡；任何失败显示原因并提供返回入口。

    面板（UI/Panels）

    [RevUIPanel(RevResPath.UI_Panel, RevUILayer.Normal)]   // 预制体路径 + 层级
public sealed class PreparePanel : RevUIPanel
{

    面板谁打开作用
    HomePanel · LevelSelectPanelGamePresentation主页与章节选择
    LoadingPanelGameFlow全屏遮挡与进度，失败时显示原因与返回按钮
    PreparePanelBattlePresentation准备期：6 张手牌、刷新手牌、开始战斗、跳过

    面板的三条规矩：交互只转发给 BattleLogic；状态用“事件触发 + 低频刷新”获得，不在 Update 里每帧读写；打开者（Presentation 或 Flow）负责在加载回调里再次核对阶段，过期面板直接关闭。

    棋盘与棋子（View）

    • BoardView是事件的主要订阅者：PiecePlaced 创建棋子、PieceHpChanged 更新血条、PieceDied 播死亡、PieceAttacked 播出手、GoStateRefreshed 刷新气眼显示。它不做任何规则判断。
    • PieceView声明 [RevPoolPrefab(…)] 并实现 IRevPoolable，所以由 RevPool 创建和回收。回池会停用物体、Awake 不会再执行，因此动画在 OnEnable 启动、OnDisable 停止（RevTimer.Every 换帧、RevMono.AddUpdate 做移动插值）。
    • BoardView.Feedback / FairFeedbackBuffer / BattleEffectView管飘字与弹道的数量预算和回收，保证密集战斗时画面可读。数值预算见《战斗性能优化规则》。
    • GameAudio订阅事件，调用 RevSound.Play / PlayBgm 播放音效与背景乐。
    异步回调最常见的坑对象池和面板都是异步取得的。回调到来时棋子可能已经死了、回合可能已经换了、面板可能已经关了。所以回调里必须带“代次（generation）”或“版本号”核对：不匹配就直接回池或关闭，不要补播。BattleHudPanel.OnEnemyDeployed 就是示范。

    动画库的分工

    棋子帧动画用 RevTimer 切换精灵；弹幕、提示条、缩放等补间用 DOTween。DOTween 的对象由创建者负责在回池时 Kill，不要 KillAll。

    GUIDE / 11

    敌方 AI：RevHeavyFSM 的用法

    敌方 AI 位于 Battle/AI，是重量级状态机的完整示例。每颗敌棋一台机器，敌方指挥一台机器。

    文件职责
    EnemyAI.cs装配与驱动：按角色注册状态，把固定模拟时间交给框架，负责释放。不含决策。
    EnemyStates.cs每个状态自己感知、切换、执行（Hold / Attack / Advance / Locked / Dead；Prepare / Deploy / Stopped），并定义宿主接口 IEnemyAIOwner。
    EnemyTactics.cs纯算法：打谁、走哪格、补在哪（围棋式评分：打吃、封逃路、切断、保眼）。无状态、无计时。
    EnemyFormationPlanner.cs回合开始时规划整套敌阵，先预检再一次提交。

    一个模拟步里的顺序：服务调 EnemyAI.Tick(秒) → 当前状态 OnUpdate 感知（死亡？非战斗？零气？有射界？移动冷却到？）→ 需要就 ChangeTo 新状态 → 立刻执行新状态的行为一次 → 行为通过 IEnemyAIOwner 提交原子动作（攻击、移动、增援落子）。

    三方分工状态机回答“现在该做什么”，算法回答“具体选哪个”，服务回答“怎样合规地执行”（扣血、占格、广播）。想改 AI，永远是在前两者里改，不要把逻辑塞回服务。

    Boss 主将：另一台更重的状态机

    普通敌棋只有五个状态，Boss 有九个技能 + 待机/死亡/停止。两者状态表差异太大，所以 Boss 主将使用独立的 BossAI，小兵与 Boss 护卫仍用 EnemyAI；同一颗棋只会有一台机器（EnsureAIFor 按“是否带王冠的主将”分流）。

    文件职责
    Battle/AI/BossAI.cs状态枚举、宿主接口 IBossAIOwner、机器装配与驱动
    Battle/AI/BossStates.cs待机决策、九个技能状态；基类实现“蓄力 → 多段命中 → 收招”的统一节奏
    Battle/AI/BossTactics.cs纯算法：技能评分挑选、范围/连线/落点/瞬移落点计算
    Services/Battle/AI/BattleService.BossAI.cs宿主：技能伤害、瞬移、回血、召唤、广播；状态机生命周期
    View/Combat/Effects/BossSkillFxView.cs预警与命中特效（DOTween + BossSkill.shader 七种模式）
    View/Board/BoardView.BossSkills.cs订阅技能事件、取池播放、瞬移瞬间对齐、换回合回收

    章节难度来自 Excel（BossSkillConfig 的 UnlockChapter 与 BalanceRule 的 Boss.*）：第一章只有横扫与狙击，逐章解锁轰炸、弹幕、瞬移、激光、汲取，第六章九招齐全；章节越高冷却越短、伤害越高，第四章起残血还会触发一次狂暴并进一步缩短冷却。

    预警与躲避：技能先广播 BossSkillTelegraph 画出危险区，命中时才按“那一刻谁在范围里”结算并广播 BossSkillCast。所以把棋子移出范围是真的能躲开——这也是为什么状态类里要在命中时重新收集目标，而不是在蓄力时锁死名单。

    不要这样做

    • 不要在纯世界目录里 using UnityEngine / UI / View / Flow。离线回归会立刻失败，这是故意的提醒。
    • 不要在界面里直接改 Piece、BoardModel 的字段。所有改变必须经 BattleLogic → IBattleService。
    • 不要在 View 里重复结算伤害。画面只播放事件带来的信息。
    • 不要订阅事件不带 owner。不要创建无主计时器。
    • 不要用 Resources.Load / File.ReadAllText 读资源。一律走 RevResManager 的逻辑路径，数据表走 RevDataTableManager。
    • 不要把策划数值写死在代码里。放 Excel 并加校验。
    • 不要手改 Generated/ 和 Revolution/。前者由导表生成；后者是框架快照，需要改能力请回源仓库。
    • 不要静默失败。返回 false 之前必须写 LastError。
    • 不要在热路径里 new List、FindObjectOfType、LINQ。复用缓冲，缓存引用。
    • 不要写单行 if。项目规范：if 后的语句必须用大括号并换行。
    • 不要把 async void 用在业务方法上。它只允许出现在按钮 / Unity 回调这类“无法 await”的边界，且要自己收口异常。
