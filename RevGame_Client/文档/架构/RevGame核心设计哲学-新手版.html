GUIDE / 01

为什么要做一个真实游戏

RevGame 的首要目标是验证 Revolution 能否支撑真实业务的持续开发。 一局远征从读表、进场、落牌，到弹道、奖励和返回大厅，每一段都给框架提出不同要求。单独加载成功一张图能证明加载入口可用。第一次进战斗图集能画、第二次进场仍然正常、退出能归还资源，才验证了这些能力组合后的结果。

这也解释了为什么项目要反复做完整链路。比如剧情粉屏会逼着团队一起看当前宿主、实际加载的资源包和 Shader。碰到通用能力的缺口，就回 Revolution 源仓库修复和验证，再把框架快照同步回 RevGame。作者在 README 里也记录了这个过程如何催生 RevCLI 和 RevMCP，项目里的实际工作决定工具要解决什么问题。

GUIDE / 02

框架提供通用能力，项目决定游戏怎么玩

想打开面板、加载图集、启动计时或借用一颗棋子视图，业务调用 RevUI、RevResManager、RevTimer、RevPool 等门面。门面就是框架承诺给业务用的入口。业务交出明确的请求，框架返回结果、句柄或失败原因。业务据此决定接下来怎么走。

为什么要守这个边界？以加载图集为例，调用者拿着同一个逻辑路径，编辑器直读和资源包加载可以各自适配。切换底层策略时，调用者继续通过原来的门面取资源。相应的代价是业务要遵守公开契约，记录谁持有引用、什么时候释放，才能获得一致的行为。

依赖也要能顺着代码查到。GameBootstrap 用 RevServices 注册 IBattleService 的具体实现，并登记持有者。想查哪个服务管理这局，就从调用处找接口，再回启动入口看注册。面板按框架约定绑定控件、刷新显示、转发点击，替换一个 HUD 时可以继续使用原有的服务与结算逻辑。

先分清三个地方的「内核」

Revolution 的通用内核
路径处理、句柄或计时器等基础逻辑。框架让这类计算尽量少依赖引擎，由适配层对接 Unity。路径处理可以拿字符串在普通 .NET 里检验，真实图集能否绑定则在 Unity 里看。
RevGame 的玩法规则
远征的棋盘、伤害和回合，无尽的敌潮与成长，九路围棋的合法落子。各自的模型或服务拥有状态。
八角笼的 C++ GameCore
给它完整帧，它按规则算出下一帧的坐标、命中、血量和指纹。裁判与客户端可以各建一个实例运行同一份规则。

GUIDE / 03

一份事实只由负责它的规则提交

拿远征一次命中来说。普通攻击、技能、战场效果都能造成伤害，护盾与减伤要遵守同一规则。EvaluateDamage 计算结果，AI 也能借它估算。ResolveDamage 核对当前目标，处理护盾与实际扣血，再完成积分、死亡等后续规则。命中事件把这次发生的事传给视图，供血条、弹道和飘字消费。

GUIDE / 04

让同一个流程负责人安排进场和收尾

一次切场涉及两个时刻。玩家点下按钮，EnterBattle 可以立即接受请求。玩家真正能玩，要等目标场景、业务域和可见画面全部接好。把这两件事交给常驻的 GameFlow，连点拒绝、异步失败、返回大厅和正常交割都能走同一套规则。

状态机 FSM 记住当前阶段
GameFlow 用 RevLightFSM 决定什么时候从大厅交割到远征。RevScene 加载 Unity 场景。选关与大厅能共用 StartScene，因为业务阶段和物理场景分别推进。
RevScope 管这段玩法拥有的对象
域是一起开始、一起结束的那批对象和工作。远征的 Logic 随战斗域启动与停止。过场遮挡要跨过旧域退出，由流程显式持有，并在新画面就绪后关闭。
Logic 按所在阶段驱动业务
BattleLogic 按固定节拍推进服务，并检查过场、阶段和教学条件。常驻服务在 GameBootstrap 注册，局内对象仍按各自的归属回收。

收益体现在第二次、第三次进局。上一局的计时和监听按归属结束，下一局的棋盘可以重新建立。域回收依赖正确的归属，图集租约、异步预热和跨域遮挡也要由持有者显式交还。切场检查故意制造交割前后的故障，等待业务进入明确结果后核对恢复。

GUIDE / 05

玩法共用基础工具，各自决定何时推进

远征、无尽、围棋和决斗真正的差别是什么事件能让规则往前走。远征和无尽在局内按固定节拍推进，各自维护回合或敌潮。九路围棋每接纳一手更新棋面。八角笼按黑白两席的完整逻辑帧推进。四种玩法仍可由同一个流程进入和退出，使用相同的场景、资源、UI 和验证入口。

无尽可以增加波次、棋心、拖牌升级和存档，在自己的服务内部采用轻量 ECS，把敌潮的移动、战斗、死亡分成系统处理。它只为需要成批处理的单位组织数据。围棋走另一条路，玩家、电脑和托管 Agent 的动作汇入 SubmitActor，再交由棋规校验。单独的局面建议供显示读取，玩法状态的写入口仍然清楚。

遇到变化时，团队能沿归属找到最小改动范围。修改无尽的成长先测无尽，若涉及双方复用的棋盘模型，再同时测远征。复用带来少写一份公共能力的好处，也带来一条明确的责任，共享契约的变化由所有调用方一起验收。

GUIDE / 06

帧同步为什么把同一份规则交给各端运行

RevGame 的八角笼采用王者荣耀同款的帧同步架构。假设两个人同一帧按下攻击，大家需要先就「第 103 帧包含哪两份输入」达成一致。权威端给黑白两席的操作排定帧号，每 50 毫秒推进一个固定步。裁判实例成功执行后发布完整帧，客户端通过 DuelCorePipe 按顺序把同样的帧交给本机 GameCore。

确定性就是同一初始状态、同一规则配置、同一输入顺序算出相同结果。C++ 内核用定点数描述位置和距离，按固定的黑白顺序处理输入，保存可复现的随机状态。这样每端都可以从同样的材料重算这一帧。对账先比较同一帧号，再比指纹。指纹不一致时，就有具体帧可以查。回放重新执行录下来的整帧，也能逐帧定位差异。

以同一帧互相命中为例。DuelWorld::Advance 先处理两席的移动和起手，收齐双方命中后再统一扣血与判胜。双方都被击倒可以判平局。这个顺序由内核固定下来，两个角色的动画先后和两端的渲染速度只影响看起来怎样。

三种时钟分开以后，延迟影响哪里

网络到达何时收到权威帧，可能一批到达
逻辑执行从上一个连续帧继续，每步 50 ms
Unity 显示在确认快照间插值，本机运动可短时预测

早期联机逐帧等两席输入，回包慢就会压低逻辑节拍。后来权威端按自己的节拍封帧，客户端用连续游标补帧，画面独立播放。2026 年 11 月 10 日的验收记录里，固定模拟 100 毫秒往返延迟的 5 秒内，权威封帧由 33 帧增到 99 帧。这个例子说明了改造的收益，条件以该次报告为准。

本机可以用独立沙盒先算起跳，Unity 只拿这份预测的位置和方向。命中、血量、胜负继续取确认快照。确认快照可以用来画角色，恢复一局还需要含垂直速度和随机状态的完整检查点。要让这套设计成立，需要保持连续帧，让各端用配套配置和原生库，再按实际网络与平台验收。

GUIDE / 07

配置只维护一个来源，资源按实际寿命持有

改一个攻击数值，规则和显示怎样一起跟上

策划可调的远征与无尽数值从 Excel 导出为数据和强类型代码，在对应玩法加载时读取并校验。决斗由 Duel.v1.json 生成 C# 和 C++ 配套配置。这样更改一处源数据后，双方可以使用同一套规则。缺项、重复、越界或指纹不匹配会在校验点暴露，排查时先回到源表。

拿一张图，为什么还要记住谁在用

业务用逻辑路径请求素材，RevResManager 按当前策略取图。图集按大厅、章节、无尽等实际用途持有，棋子与特效通过池复用。退场先让旧回调失效并归还对象，再释放图集和预热持有的引用。共享图集仍被下一屏使用时，可以继续留在内存。

策划调攻击数值时回到源表，美术换弹道时沿资源映射和表现层改素材，程序修改命中条件时回到规则服务。各自的修改通过已知的配置、路径和结果数据接在一起，联调时可以先核对这次改动触及的那一环。

2026 年 11 月 9 日的粉屏复盘给出了很实际的理由。桌面 Editor 使用真实 AB 时，活动构建目标和实际运行宿主可能不同。Windows Editor 要取配套的 PC 资源包。修复后走相同逻辑路径的业务调用仍然成立，验收则要核对实际包、Shader 和冷启动画面。

GUIDE / 08

性能优化先找哪些工作可以少做

棋子掉血时，血条要更新。棋盘位置、加气与围困免疫都没变时，气眼结果可以复用。BoardModel 的落子、移动、移除、清盘负责更新占格版本。RefreshGoState 把占格、加气与免疫一起作为判断条件。有任何一项变化，就重新计算并通知视图。

这条边界也给优化定了验收条件。同一棋盘、同一组动作，优化前后要核对气眼、死亡移除和战斗结果。AI 可以在自己的深快照上试阵，避免移动实战棋子触发占格变化。画面压力则另外看弹道池、飘字预算和共享材质。把规则耗时与显示耗时分别测量，才能判断减少的是哪一份工作。

GUIDE / 09

把「改对了」变成能检查的结果

玩家与开发测试能走同一个业务入口，规则的失败原因、已提交状态和离场结果都能读取。以进远征为例，测试先发起正常的进入请求，等过场结束，查实际场景、棋盘和手牌。再走正常返回入口，检查旧域的工作、对象和资源是否按归属收尾。

RevGM 和 RevRuntimeAutomation 把开发态能力注册出来。RevMCP 可以发现真实入口、执行动作、读取结果并跑带清理的计划。它给自动化提供的是可执行的业务契约，所以人和工具可以用同一组条件判断本次改动。

RevGame 对 Revolution 的验证结论现有工程和验收记录表明，Revolution 的门面可以组合起来承载多模式的流程交割、资源与对象生命周期、界面和业务自动验证。远征、无尽、九路棋规、原生帧同步各自保有规则和验证入口。编辑器、真实资源包、联网同帧和真机性能分别有自己的证据范围。

下次看一个改动，先回答三个问题

  1. 谁有权改变这份状态？扣血和胜负找规则，改动画节奏找表现，切换整段玩法找流程。
  2. 这个对象应该活多久？随面板、随局或常驻，决定它在哪登记和在哪归还。
  3. 怎样知道这次改对了？固定输入，写清成功、拒绝和退出后的可观察结果。
