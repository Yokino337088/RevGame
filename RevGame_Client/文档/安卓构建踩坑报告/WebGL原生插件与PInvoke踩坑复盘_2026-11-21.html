01 · Windows DLL 与网页原生代码

RevGameCore.dll 是 Windows x64 的原生库，由 Windows 宿主按名称加载。Android 走对应架构的 libRevGameCore.so。WebGL 使用 Unity 配套 Emscripten 编译出来的 wasm32 对象，把 libRevGameCore.a 静态链接进最终 Player 的 Web.wasm。浏览器执行同一套 C++17 决斗逻辑，通过编译阶段绑定的 C 函数推进帧。Unity WebGL 原生插件

之前的工程只提供 DLL、Android SO 和 DllImport("RevGameCore")。这些文件足以让 Editor 和原生应用调用内核。原 Web 包可以进入大厅，真正进入决斗后才会构造原生实例。Web 适配需要补齐静态库和声明，判断依据是实际调用链、构建参数和归档里的导出。

02 · 编译、检查符号和导入 Unity

  1. 找到生成 Player 的 Unity Editor。RevGame 使用 2022.3.15f1c1，自带工具链位于 Editor/Data/PlaybackEngines/WebGLSupport/BuildTools/Emscripten。
  2. 用配套 em++ 将 C++17 源编译成 wasm32 .o，用 emar rcs 生成 .a。脚本给子进程传入 EM_CONFIG 和 PYTHONUTF8=1。当前 Web Player 使用单线程配置。
  3. 把现有的 Tests/PipeChecks.cpp 链接同一归档，用工具链自带 Node 运行。检查通过后，脚本将归档更新到 Unity 插件目录。
  4. 在 Unity 的 Plugin Inspector 中给 .a 及 .jslib 只启用 WebGL，保留各平台插件自己的 .meta。libRevGameCore.a 和运行时入口脚本的导入设置随代码入库。
$editor = "E:\Unity安装\2022.3.15f1c1\Editor\Unity.exe"
$archive = "RevGame_Client/UnityProject/RevGame.Unity/Assets/Plugins/RevGameCore/WebGL/libRevGameCore.a"
py -3.13 -X utf8 RevGame_Client/RevGameCore/BuildWebGL.py --unity $editor --output $archive
$emscripten = Join-Path (Split-Path -Parent $editor) "Data/PlaybackEngines/WebGLSupport/BuildTools/Emscripten"
& (Join-Path $emscripten "llvm/llvm-nm.exe") --defined-only --extern-only $archive

用 Unity 的工具链重新构建插件后再打 Player。把原生对象交给其它版本的 LLVM 或把 Windows 的 .lib 当成网页归档，都可能在链接阶段失败。Unity 2022.3 支持由 Wasm 对象组成的 .a，项目使用的归档是 16,458 字节。Unity 原生工具链版本对应表

03 · C ABI 与托管调用怎么写

给跨语言边界一个稳定名称

C++ 使用 extern "C" 导出。RevGameCore 的接口只暴露实例指针、显式长度和定宽整数。原生对象、异常、容器和内存所有权留在调用契约明确的一侧。托管数组只在调用期间借给原生函数。

extern "C" {
    void* GameCore_Create(void);
    void GameCore_Destroy(void* handle);
    int32_t GameCore_Write(void* handle, const uint8_t* data, int32_t size);
}

实际头文件还声明 GameCore_Read、GameCore_SaveCheckpoint 和 GameCore_RestoreCheckpoint。六个符号都应在静态归档中能找到。

用运行平台选择 P/Invoke 库

#if UNITY_WEBGL && !UNITY_EDITOR
private const string Library = "__Internal";
#else
private const string Library = "RevGameCore";
#endif

[DllImport(Library, CallingConvention = CallingConvention.Cdecl)]
private static extern IntPtr GameCore_Create();

[DllImport(Library, CallingConvention = CallingConvention.Cdecl)]
private static extern void GameCore_Destroy(IntPtr handle);

Unity 的 WebGL 活动目标和桌面 Editor 的运行宿主是两回事。Editor 仍走 Windows DLL。浏览器从最终 Wasm 内解析静态符号。DuelCorePipe 用已有的 SafeHandle 封装 IntPtr，一局独占一个实例。结束时走 Dispose 释放。原生输出数组在声明中标为 [Out]，缓冲与字节长度保持配对，失败不会越过原有 FIFO/检查点边界。

生成的 IL2CPP C++ 声明直接引用 GameCore_*，链接器据此从归档取出所需对象。决斗每帧走模块内调用，浏览器脚本只承担需要 DOM 的退出动作。

读错误时先看是哪一层

04 · 「我不玩了」为什么会停在原画面

按钮原来从 HomePanel.OnQuit 走到 GameFlow.RequestQuit，网页与其他 Player 都在同一分支调用 Application.Quit()。即使 Unity 停止了 Player，外层网页也仍由浏览器控制。旧模板既没有接收退出意图，也没有处理浏览器标签页，于是只留下最后一帧。

  1. GameFlow.RequestQuit 在网页端先尝试提交 PlayerPrefs，再通过 __Internal 请求 RevGame_RequestBrowserQuit。保存调用出错仍会交付退出。
  2. RevGameBrowser.jslib 从当前 Module.canvas 派发 revgame:quit，让 Wasm 原点击回调先返回。
  3. RevGameFullscreen/index.html 接到事件后显示退出状态，同一页面只执行一轮 unityInstance.Quit()，最多等待 1,500 ms。
  4. 试玩入口的「开始游戏」在真实用户点击里打开 ?play=1 的游戏标签页。退出时脚本关闭该页，入口页可再次启动。浏览器拒绝关闭手动打开的标签页时，网页释放当前 Player 并返回入口。
// C# · 仅在 WebGL Player 编译这一声明
[DllImport("__Internal", EntryPoint = "RevGame_RequestBrowserQuit")]
private static extern void RequestBrowserQuit();

// JavaScript · RevGameBrowser.jslib
mergeInto(LibraryManager.library, {
    RevGame_RequestBrowserQuit: function () {
        var canvas = Module.canvas;
        setTimeout(function () {
            canvas.dispatchEvent(new Event("revgame:quit"));
        }, 0);
    }
});

浏览器允许脚本关闭由网页正常创建的部分浏览上下文，也会考虑历史记录和沙箱条件。退出链因此由页面控制，并提供明确的返回入口。Unity 网页模板 Quit API · HTML Window.close 规则

05 · 怎样证明它真正生效

  • 原生层使用同一静态库运行 FIFO、检查点、恢复和确定性回归。Windows 使用现有 tools/DuelPredictionChecks 校验预测与本地人机节拍。
  • Player 层核对 WebGL 正式版 BuildReport 与六个 GameCore_* 的实际 IL2CPP 绑定。浏览器从真实人机入口打到决斗或使用受控开发专用夹具，观察原生快照推进。
  • 网页层从启动入口创建游戏标签页，用真正的大厅按钮触发退出。记录 Child 是否关闭、启动页是否保留以及再次启动是否可用。用单独案例验证拒绝关闭后的返回入口。
