WEBGL / 01

值得做大厅入口的域内预热

WebGL 里 LoadAsync 能让当前画面继续跑。点击后如果才去下载 AB、读图集、装配控件，面板仍得等这些步骤。提前拿到一份可以复用的资源引用，玩家打开时就能跳过冷读或接上已经发出的请求。现有启动已准备首页和选关，战斗首屏也有自己的资源交接。

这一版的「意图」来自大厅里实际可点的入口。按设置、玩家对战、无尽顺序准备对应预制体，最后把无尽的 EndlessMenu 图集对象读入缓存。它们都有稳定的正式资源路径，使用同一个 RevUI 元数据和 Revolution 缓存。实际点击仍走原有 OpenAsync 及图集可画条件。

要决定的事怎么做可核对的边界
何时发出大厅面板打开后等揭幕，检查同一域、首页和可交互状态，再每次读取一项。首屏交接、前台操作与战斗各有自己的入口。有覆盖或退域后停止提交后续候选。
提前拿什么只准备三个入口预制体和一个明确的图集对象。AB 的包与依赖由框架按真实映射解析。例如 ui_endless 本体约 16 KiB，依赖的 atlas_endlessmenu 约 1.02 MiB。算开销要看整条依赖。
资源谁收尾加载一开始就把具名租约交给原大厅域。成功持有到退域，失败提前还给框架，前台仍可按正常入口重试。预热和真正打开可以共享在途下载，引用分别计数。换域后，旧请求只完成资源收尾。

继续扩展到某个域时，先量那个入口有多少次冷等、提前准备能减少多少时间，以及依赖多花的流量与内存。稀有页面和整章战斗资源适合沿已经存在的按需加载或场景交接。

WEBGL / 02

分别压住绘制像素和表现峰值

网页画布。CSS 画布继续铺满视口，DPR 高时把实际绘制缓冲等比限制在约 1600 × 900 像素的总量。尺寸由视口或全屏变化触发，同尺寸直接复用。以 1366 × 768 的 CSS 视口和 DPR 2 为例，原请求约 420 万像素，预算后约 144 万，像素数少 65.7%。原画、章节动画和棋盘安全区继续通过原来的渲染流程。Unity WebGL Canvas 尺寸说明

远征反馈。浏览器有独立的同屏名额和每帧投射上限。继续使用原来的事件、按来源合并、弹道公平队列和对象池。战斗先照常产生攻击与伤害，表现层从已经结算的事件里选择同屏显示。分帧预建对象池取同一组上限。

WEBGL / 04

复测用同一负载和同一设备

  1. 保留旧包和新包，固定浏览器版本、硬件加速、视口、DPR 和网络条件。用全新的浏览器配置测冷首开，同一个域里的重开另记。
  2. 走首页的正式按钮，核对可见面板和实际的 AB 请求。按同一条件过早点击、退出域和重进，检查旧任务没有交付到新域。
  3. 战斗从实际流程准备固定棋数，再核对进入战斗、攻击继续结算、屏幕可操作和退场回首页。采样窗口留给游戏，截图放在窗口以外。
  4. 目标为约 60 FPS，明确记录 P95、P99、最长间隔和超过 25 ms、50 ms 的次数。先看尺寸与战斗阶段，再定位浏览器主线程、GPU 或首次资源读入。
60 FPS 目标的验收范围。第四章 81 棋对照接近 60 FPS。第六章同一规模的多轮结果仍从约 45 到 60 FPS 波动，偶发超过 50 ms。稳定 60 FPS 仍未验收通过。以上为本机 Edge 和这些短窗口，长期运行、移动浏览器以及其他场景的极限负载需用各自设备和用例验证。

同机分开看帧间隔与主线程长任务。尺寸下降后仍有长任务时，应回到对应帧核对 CPU、显示提交、GPU 与调度。当前数据不足以把第六章的长帧归到某个具体代码段。
