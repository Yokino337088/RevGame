# RevGame · 战斗性能优化规则

版本 1.0 · 2026-10-18 · Unity 2022.3.15f1c1 · Revolution 框架验证项目

本规范约束今后的战斗逻辑、渲染、UI、动画、内存和资源构建。固定 **1920×1080 横屏设计基准**，不通过缩小棋盘、减少六张手牌、降低既定反馈密度来掩盖性能问题。先测量，再改实现，最后同时验证性能与玩法。

本文件与同目录浅色 HTML 内容同步；仓库 `AGENTS.md` 将它作为后续战斗开发入口。Revolution 门面、资源引用计数和分组规则来自框架；图集划分、数量预算、具体测试门禁是本项目在其基础上增加的约定，不冒充框架自带能力。

## 01 · 实测结论与适用边界

| 指标 | 优化前 | 本次结果 | 测量口径 |
|---|---:|---:|---|
| 固定战斗画面绘制批次 | 24 | 13 | Editor DX11，events 场景，暂停模型推进，110 个启用的 SpriteRenderer |
| SetPass 次数 | 17 | 10 | 同一画面；材质/Shader 状态切换次数 |
| 可见 SpriteRenderer 使用的不同贴图 | 13 | 5 | 包含 Unity 内置血条白片，不含独立 UGUI 统计 |
| 相同战斗/UI根资源的纹理对象 | 172 | 8 | 分别加载旧/新 PC AB 的同一组根资源及依赖 |
| 上述纹理原生内存估计 | 9,009,968 B | 7,219,172 B | Profiler.GetRuntimeMemorySizeLong 合计，约减少 **19.9%** |
| 图集覆盖 | 无 | 9 图集 / 191 图片 | 所有 GameRes 图片及打包、场景可达图片；唯一归属 |
| AB资源布局 | 19 包 | 25 包 / 235 映射 | PC 和 Android；外部导出目录不入库 |

**不能从这些数字推出手机稳定 60 FPS。** 当前证据来自 Unity Editor 与 PC AB，没有 Android 真机 GPU 耗时、温度和峰值内存数据。纹理原生内存不是进程总内存，也不是显卡驱动的真实显存占用。固定画面不等于整场战斗峰值。

前一轮已完成规则 CPU 优化：同一离线夹具战斗中位耗时 291.343 → 40.912 ms，AI 补子 13.773 → 3.557 ms。它们是一次测试工作量的执行时间，不是每帧耗时。本次不把历史数字重复计为新增收益。

一个实际反例：第一版把备用 UI 混入常用图集，纹理内存变成 9,840,612 B，比原先更大。拆出 `UIReserve` 后才降至 7,219,172 B。**“打了图集”不等于“省了内存”。**

## 02 · 如何选择渲染优化

| 技术 | 本项目决定 | 原因与验收方式 |
|---|---|---|
| SpriteAtlas + 共享材质 | 立即使用，已落地 | 同一贴图、材质、相邻排序的精灵更容易合批；实际检查 Renderer 的 sprite.packed 与纹理对象 |
| 动态合批 | 保留并验证，已在工作 | 基线已出现动态合批，不能把打开一个开关算成新增收益；用 Profiler / Frame Debugger 检查 |
| GPU 实例化 | 当前不强行改造 SpriteRenderer | 当前实例化批次为 0；Shader 的 multi_compile_instancing 只提供变体，不会自动把 SpriteRenderer 改成实例化渲染器 |
| UGUI 合批 | 由 Canvas 按贴图、材质、遮罩和层级组织 | 不等同于 MeshRenderer 的动态合批；同图集也可能被文字、不同材质、Mask、Canvas 打断 |
| SRP Batcher | 不能直接套用当前 Built-in 项目 | 它不是“把多个对象合成一次Draw Call”；更换渲染管线必须独立评估迁移成本 |
| 静态合批 | 不用于移动棋子和弹道 | 棋子换位、动画换帧、弹幕飞行都有动态变化 |

GPU 实例化值得在“数量远超当前 9×9 棋盘，且 CPU 提交成为瓶颈”时做隔离实验。实验渲染器须统一 Quad Mesh、材质和图集，传入每实例矩阵、颜色、UV矩形、帧号，并处理透明排序、裁剪、Boss 尺寸、对象池以及移动端回退。没有与现有 SpriteRenderer 同内容、同设备的性能对比，不替换正式路径。

动态合批也有 CPU 顶点变换成本。不要为了一个批次把不相邻的透明物体乱排序；文字遮挡次序、弹道轮廓和拖尾正确性优先。最终检查 Batches、SetPass、CPU Render Thread、GPU 时间和透明过绘，不能只盯 DC。

## 03 · 图集与AB的强制规则

所有进入 AB 的**项目 Sprite 图片**必须恰好属于一个 Sprite Atlas V2；不允许业务绕回散图 Texture2D 加载。引擎生成的字体字形纹理、内置 UISprite、RenderTexture、法线图或 LUT 不是 UI Sprite，不能为了满足字面要求错误打入 SpriteAtlas。新增特殊纹理要明确用途，当前构建门禁对未分类的非 Sprite 图片报错。

| 图集 | 内容 | 加载边界 |
|---|---|---|
| PieceFrames | 玩家/敌人 135 张序列帧 | 棋子与手牌头像共享；离开战斗释放服务自己的租约 |
| CombatFrames | 死亡、升级、弹头等 14 张特效图 | 战斗按需加载；回池后再释放资源 |
| BoardStatus | 格子、眼、被围三帧、棋子配件，共 11 图 | 棋盘/战斗表现共享 |
| UIBattle | 当前使用的手牌、对战底板、行动条和状态图 | 与实际 UI 使用者共享 |
| UIMenus | 当前使用的菜单按钮和提示底图 | 首次请求加载 |
| UIReserve | 当前没有预制体/配置引用的备用 UI | 打包保留，正常游戏不主动加载 |
| UI_Tavern_imgBKAtlas | 备用酒馆大底图 | 独立页面，避免挤大常用图集 |
| UI_chessBoard_chessBoardAtlas | 备用长棋盘大图 | 独立4096上限；不恢复成正式棋盘背景 |
| SceneBackdrop_0fc7e394Atlas | 第一章专用原背景 | 仅第一章按需租用；与第一章图片/材质/Shader同包，其它章不预热 |

生产入口是 `GameResourceBuild.Configure / BuildAndCopy`。图集工具只给 Revolution 提供资源布局，不另造 AB 加载系统。新增图片后执行配置、构建、复制，提交生成的 ResMap、RevResPath 和图集目录清单。

1. 通过 AssetDatabase 移动资源并保留 `.meta` GUID；不用文件系统复制“第二份兼容图片”。旧编辑器配方走 `GameArtPaths` 迁移表。
2. 常规图集最大2048，备用超大图独占页面。关闭旋转、Tight Packing、Read/Write、Mipmaps，双线性过滤、4像素间隔。保留九宫格 border、pivot、PPU 和序列帧顺序。
3. PC 使用 BC3/DXT5，Android 使用 ETC2 RGBA8，保留透明通道。ETC2 不支持的设备可能产生回退解压，发布前须核对最低设备范围；不以Editor结果代替真机。
4. 图集 `Include In Build=false`，通过 Revolution 加载 AB。源图与所属图集同包；预制体、材质、字体、Shader 保持明确共享包归属。
5. 使用 `.spriteatlasv2` 和 `SpriteAtlasImporter`。只创建 V1 的 `new SpriteAtlas()` 文件，在 V2 工程里可能得到无正确打包数据的资产；必须检查实际AB中的图集帧数及像素页面。
6. 构建前检查：图片覆盖且唯一归属、同包、命名、漏标、重名、循环依赖、隐式重复依赖、Android Shader。
7. 构建后检查：实际AB加载、图集不为空、Sprite已packed、没有源Texture2D副本、UI/序列帧/背景UV正确。
8. 增量构建后按本次Manifest清理改名后遗留的旧包，再复制到StreamingAssets。只清理经过绝对路径校验的项目AssetBundles平台目录中的旧文件对，不能递归清理任意配置路径。本次移除了不再被清单使用的art_ui、shared_piece_frames、shared_status旧包。

**资源路径仍可保留 Sprite 的兼容映射，但运行期不能按 Texture2D 加载这些图片。** Unity 会剥离源图片像素；直接请求 Texture2D 与本规范冲突。现有预制体与配置保留 Sprite GUID，Unity 在图集加载完成后自动绑定到图集页。

2026-10-23补充：六章背景分别归入六个自包含AB。第2~6章为Shader独立采样的Default纹理，不作为Sprite使用；每章专属Shader与材质同包，不再归公共Shader包。GameScene不硬引用章节图或材质，切章/退出成对归还，空闲整理点卸载。实测见[章节背景专题](../进度同步/章节背景独立Shader与六章分包-2026-10-23.html)。

## 04 · Revolution资源与内存生命周期

资源寿命链：逻辑路径 → RevResManager.LoadAsync → 句柄检查 → 使用 → Release → 未使用缓存 → 流程空闲边界 FlushUnused。`Release` 不等于立即把整个进程内存降回原点，池、依赖和引擎缓存可能仍持有对象。

`GameSpriteAtlasService` 只适配 Unity 的 `atlasRequested`：按生成白名单验证标签、合并同图集在途请求，再通过 `RevResPath.Atlases` 加载。它没有自行拼 StreamingAssets 路径，没有每帧 GetSprite，也没有每颗棋子复制一套帧图。

| 对象 | 所有者 | 收尾要求 |
|---|---|---|
| 图集加载租约 | GameSpriteAtlasService 的 Entry | 每次Load配一次Release；失败和迟到回调同样收尾 |
| 战斗棋子/格子/反馈 | BoardView + RevPool + 战斗域 | 回收视图、清回调和队列，再处理资源 |
| Tween | 创建动画的视图/卡牌 | 回池Kill(false)，清字段；禁止全局KillAll误伤其它UI |
| 计时器、事件 | RevScope / RevLogic / 显式owner | 退出域或销毁时取消；不能无主订阅 |
| 图集GetSprites测试克隆 | 测试夹具 | 用完销毁克隆；正式动画不走这条路径 |
| 共享材质 | 资源系统/场景 | 用sharedMaterial，不通过renderer.material隐式克隆 |
| CPU查询工作区 | 单个BoardModel/服务实例 | 清内容保容量，不能用全局可变静态容器串局 |

禁止在每帧、每次攻击、每张卡点击时调用 GC.Collect、Resources.UnloadUnusedAssets 或强制清整个资源组。`UnloadGroup(force:true)` 会伤到仍在用的共享引用；图集服务使用 Scene 组隔离战斗域强制回收，并在退出战斗后延一帧显式释放战斗专用租约。所有后台回调都检查已释放状态和流程版本。

小白注释模板：类说明“负责什么、不负责什么、谁创建谁销毁”；字段说明“含义、单位、范围、是否共享、什么时候清”；方法说明“输入、结果、失败、调用时机、所有权”；实现中的关键步骤说明“为什么这么做、先后顺序、错误做法会造成什么”。不要给每句赋值机械写“将A赋给B”。

## 05 · CPU、分配与战斗算法

- 棋盘占格只通过 `BoardModel.Place/Move/Remove/Reset` 更新，同时递增 TopologyVersion；不得直接改位置后跳过占格维护。
- 气眼计算只在占格、加气、围困免疫变化后刷新。伤害致死、补子、移动、复活都可能改变拓扑，不能漏刷新。
- AI 同一轮查询复用独立深快照，候选试算后还原；禁止移动真实战斗棋子试走，禁止让多个AI共享可变草稿。
- 高频查询由调用方提供 List/数组缓冲。禁止在热循环里 LINQ、ToArray、闭包排序、字符串拼接、扫描整个场景和重复 GetComponent。
- 高频容器预留容量并有上限。值类型并非万能：装箱、接口枚举器、复制大struct也可能有成本。
- 敌方 AI 决策按既有战斗时钟触发，不能改为每帧寻路或每帧扫描所有候选点。表现帧与规则步长分离。
- 飘字每帧先取至多20个矩形快照，再作最多400次轻量矩形比较；摆位的25个候选位置共用一组预留矩形。不要在双重循环反复读取Renderer.bounds和坐标转换。
- 遮挡透明度没变化时不重复写TextMesh颜色；但Tween自身淡出必须继续更新。

目标是热路径稳定且分配可解释。当前 Mono 中 `GC.GetAllocatedBytesForCurrentThread()` 曾对已知分配也返回0，不能用它证明零GC。使用 Profiler 的 GC.Alloc 调用栈/ProfilerRecorder有效计数和Player长时间记录；区分首次字体扩容、对象池预热和稳定期。

## 06 · 弹幕、动画和UI预算

2026-10-24按用户新要求更新：远程活动弹道上限35，待播70，每帧最多6发；数字取消0.22秒等待，同帧合并后每帧最多8条，满屏优先替换口号、其次最旧数字。待播伤害最多81个目标；这属于有限画面预算，不保证超负载时每一击都单独停留。预热71个共用反馈池对象（20文字+35弹道+16近战）。五职业原画和两张近战原画统一进CombatFrames；10个弹体/尾迹材质、3个魔法环材质和3个近战材质均共享单Pass，不逐对象复制。参数块发射时同步绑定图集页与局部UV；其对合批的成本需计入，不能宣称零额外Draw Call。

历史验收数字保留原测量口径，新增证据见[本次视觉升级](../进度同步/视觉升级-2026-10-24/report.html)。

| 项目 | 约束 | 超限行为 |
|---|---:|---|
| 同屏飘字 | 最多20 | 合并同目标伤害；有界队列；过期不补播 |
| 攻击口号 | 最多7，计入20总预算 | 同棋子冷却；优先保留伤害信息 |
| 活跃弹道 | 最多35 | 分批释放，不能无限创建 |
| 近战短效 | 最多16 | 独立预约计数；过载舍弃表现，不影响已结算伤害 |
| 弹道待播 | 最多70 | 限龄丢弃过期表现，伤害早已在模型结算 |
| DOTween预留容量 | 512 Tween / 128 Sequence | 是容量基线，不是允许无限动画的理由 |
| 文字遮挡 | 避让优先；下层35%透明度兜底 | 保留字与描边的透明排序 |

对象池优化的是重复创建/销毁，不会让活跃对象免费。每个弹道还有轮廓和短尾，35条弹道最多对应105个SpriteRenderer，测绘制时必须算子层。文字描边也会增加顶点和透明过绘。数量、材质、纹理与屏幕覆盖面积都要限制。

2026-10-24追加：区域波动使用每格共享Shader与参数块，只动画覆盖层；列阵规划使用独立深快照，模型先提交再显示DOTween。新增动态效果不代表合批收益；验证与边界见[战斗冲击与战术升级](../进度同步/战斗冲击与战术升级-2026-10-24/report.html)。

切回合顺序固定：使旧异步代次失效 → 取消动画/计时器 → 归池 → 清文字、弹道、待播队列与预约计数 → 建立下一回合。任何迟到结果只能归池，不能占用新回合预算，不能再次扣血。

UI继续按1920×1080横屏布局，适配安全区但背景覆盖整个视口。UGUI依靠图集、共享材质与合理层级合批；不为每张卡建一个Canvas。只有Profiler证明频繁重建影响其它静态UI时才拆Canvas。静态数值没变化不反复改Text，非交互图片关闭Raycast Target，避免每帧Layout重建。

## 07 · Shader与图集UV

棋子、卡牌、面板和背景优先单Pass共享材质。不加GrabPass、全屏模糊、逐棋子RenderTexture或高成本屏幕后处理。透明部分仍保持alpha，避免方框、残影和过绘扩大。

UI原图使用UV0，动画效果使用独立局部坐标UV1，不能用图集中的绝对UV作为每张卡的0~1坐标。动态背景先将图集UV还原为原图局部坐标，再扭曲、限制范围，最后映回图集矩形；否则会采到邻图或透明间隔。

`GamePresentation.UpdateBackgroundAtlasUv` 使用 `DataUtility.GetOuterUV` 取得四个数。它不取会分配数组的 `sprite.uv`；只有UV改变才更新缓存的 MaterialPropertyBlock。背景只一张允许独立参数块；不要把这个做法无条件复制到所有棋子而打断合批。

修改 Shader 后检查：透明边缘、九宫格、卡牌翻转、Boss三帧、被围三帧、不同屏幕比例、Android编译和真实AB材质。`shader.isSupported` 只是基本检查，不等于真机所有变体都正确。

## 08 · 编程与注释规范

1. 业务只访问Rev门面；禁止绕进Core/Implementation，禁止修改本仓库的Revolution框架快照。需要框架能力时回源仓库修改、验证、重新导出。
2. 流程用唯一GameFlow + FSM + RevScope；规则留在服务/模型，UI交互只转发，表现事件不二次结算伤害。
3. 异步只用RevTask及框架回调。每个回调审查退出、重入、失败和对象回池四种情况。
4. 面板分OnBindView装配、OnRefreshView落屏、交互转发。面板用CloseSelf，不直接Destroy自己。
5. 资源用生成逻辑路径或两段式参数，首次真机异步加载并检查句柄ErrorReason；日志走RevLog。
6. 中文注释；方法体有大括号；方法签名的左括号与参数不另起一行。核心类、接口/实现契约、方法、字段和关键算法步骤必须有面向新手的解释。
7. 按业务层和模块细分目录：例如View/Resources、View/Combat/Effects、Services/Battle/Simulation。Editor代码统一在Assets/Editor/RevGame下，不能塞进GameScripts/Editor。
8. Shader放GameShader对应子目录；材质放GameRes/Material对应子目录；UI/Panel与UI/Item分开。生成目录不任意迁移。
9. 外部AssetBundles、Library、Temp、Logs、csproj/sln、安装包不入库；用户指定Assets/StreamingAssets可入库。

## 09 · 后续优化执行顺序与门禁

|---|---|---|

下一阶段在目标Android设备做10分钟密集战斗与反复进出：记录CPU主线程/渲染线程/GPU p50与p95、GC.Alloc、进程与纹理峰值、温度降频和触控响应。60 FPS预算16.67 ms，30 FPS预算33.33 ms；这是目标预算，只有设备证据才能标记达标。

如果GPU受限先查透明过绘、Shader采样、像素覆盖和分辨率成本；如果CPU渲染提交受限再评估实例化；如果GC受限查分配栈；如果内存增长查仍被引用的池对象、事件、Tween、图集Entry和依赖链。不要把所有瓶颈都归因于Draw Call。

## 10 · 验收与证据

同目录 `验收记录` 保存基线、最终资源内存对比、图集Play断言、资源和可读性回归、图集AB二进制检查、HTML排版检查。当前报告明确区分编辑器证据与待做的真机测试。

本次通过：9张真实AB图集/191张Sprite，3次战斗重入引用释放；231个资源加载；50条密集反馈断言（峰值20条文字/14条弹道）；136条回合清理回归；37条Shader/动画回归；649条规则、13,418条随机棋盘等价断言、737条横屏布局断言。9个PC图集包均没有额外的源Texture2D资产；PC与Android各25包构建成功。HTML在1440和390宽度下无页面溢出、无脚本错误，交互、目录、链接及减少动画模式通过。

纹理内存基线来自修改前提交be72a8c的PC AB，解出到临时目录，不回滚工程。复测入口：`GameAtlasMemoryChecks.Compare("Temp/AtlasBaselinePC")`，仅在非Play使用。固定画面前测为Editor直读，后测为实际PC AB，均为events场景、110个启用SpriteRenderer；数字反映该样本，不承诺所有场景同样降幅。

框架可行性结论：本次图集通过项目适配器接入Unity绑定事件，加载、计数与释放复用RevResManager；棋子/弹幕仍复用RevPool，流程仍由RevScope/FSM驱动，生产构建仍复用Revolution AB工具，**没有改框架内核**。需要在项目侧补充的能力是图集分类、覆盖门禁、绑定适配和真实AB验收。
