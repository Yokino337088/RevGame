PRACTICE / 01

先读懂一帧花在哪儿

60 FPS 约给每帧 16.67 ms。平均 FPS 反映一段时间画出了多少帧，整帧 P95 表示约 95% 的采样帧在这个耗时以内。想找偶发卡顿，要同时看 P99、最长帧与超预算次数。先固定设备、资源、分辨率和战斗输入，再选要优化的一段。

第五章的教训。同一份 81 棋压力用例里，六章整帧 P95 有升有降。第五章单独把相机布置做同进程配对后，每帧相机 CPU 从 17.55 降到 13.33 µs。整帧慢了时，先找到那一帧真正运行了什么，再分别看逻辑、特效、提交、GPU 与 Present 后等待。线程和 GPU 有重叠，计时显示在不同列。 六章逐段数据与第五章复核

2026-11-19 的另一次本机 81 棋诊断里，第五章最慢的 111 帧只有 11 帧执行了固定步。普通组到慢帧组，GPU 中位数为 1.076 → 1.186 ms，调用 Present 到下帧开始的间隔为 0.221 → 3.510 ms。最长的变化出现在提交画面之后，窗口、驱动和编辑器各占多少仍待测。

PRACTICE / 02

用缓存省掉 CPU 的重复计算

棋盘里有很多相近的问题。阵容评价、攻击预测和敌方 AI 可能在同一逻辑步多次询问一枚棋能打到哪些格子。可以复用的是几何结果。棋子的坐标、走法、障碍或棋盘版本变化时，再算受影响的射界。当前 HP、护盾和威胁值留到实际评分时读取。

实现前写清缓存的所有者、键的输入、失效入口、容量和清理时机。缓存命中时还要保证候选顺序一致，因为平分时的取舍会改变战斗。

私有试盘。AI 预测把必要状态复制到调用者独占的草稿，用完还回本轮租约。复制要覆盖 HP、气眼、Buff 和其他会影响结果的字段。这样可安全复用容器容量，正式棋盘不会被预测过程改动，真实伤害仍只提交一次。

RevGame 在固定 4800 次射界查询中测到 13.302 → 0.309 ms，100 次深试盘含气眼刷新耗时 4.643 → 3.575 ms。这些是局部操作数据。移动会触发重算，所以固定盘的高命中率要和真实变盘的命中率、顺序和回放结果一起看。 棋盘查询源码 · 计时与回归证据

PRACTICE / 03

逻辑步管结算，表现帧管运动

远征原本按固定步结算，落格后由棋子视图补间。决斗从确认帧快照采样。无尽每 100 ms 提交一次逻辑状态，更新前的外围网格直接画确认位置，两次更新之间会停在原处。现在竞技场采样已提交的状态，画面按自己的帧率补出中间位置。模拟仍按原步长更新移动、索敌、伤害与胜负。

  1. 收到新样本再整理对象。以局次、逻辑时间、显示变更版本和槽代次判断采样是否失效。敌人身体、血条和出生效果共享插值坐标，减少重影。
  2. 每帧只提交变化的数据。同一队列内把位置与颜色/UV 分成两个顶点流。普通补间帧只送位置，换帧、掉血或显示归属变化时更新外观。出生特效只跟踪实际在播的视图。
  3. 遇到断点就重新对齐。击退跳位按招式语义当步生效，复用槽位时按新身份初始化。暂停、退局、重入各按原入口复位。必须交付的受击与死亡回执独立消费。

插值在已经画出的画面之间补齐运动，常规位移会用约一个逻辑步追到确认位置。GPU、UI 或大特效导致整帧没按时出图时，继续测对应阶段的耗时。 敌潮采样源码 · 双顶点流实现 · Unity 顶点缓冲接口

PRACTICE / 04

让渲染提交和 GPU 聚焦可见内容

CPU 准备并提交绘制指令，GPU 处理顶点和屏幕像素。共享材质和图集能帮助相邻对象合批。透明对象还要保持遮挡顺序。同一像素被多层透明对象反复绘制叫过绘。GPU 忙在大面积叠加或噪声采样时，先量覆盖范围与有效 GPU 帧时，再决定用哪种做法。

无尽先把活跃敌人与受伤血条排成连续范围，按实际数量写网格索引。缓冲可容纳 1024 敌，不在网格里留 1024 个可绘制方块。RTX 4060 Editor 的 240 敌压力段，整帧三角形均值减少 61.1%，P95 从 6.451 降到 5.551 ms。这个案例对应旧的网格范围改造，与后续双顶点流是不同交付。 分场景实测与实际方块数

换成 Compute 前，先把完整成本算进去

第四章沼泽本机试验保持原画和最终合成，两种预计算都以 30 Hz 更新 960×540 的 RGBAHalf 流场。一个场约占 3.96 MiB 像素存储。先写中间纹理，再采样来合成，会增加写入、带宽和调度成本。只有当原本重复的运算省得更多时，预计算才划算。

PRACTICE / 05

复用内存容量，及时归还引用

分配和驻留是两条指标。每帧建列表或拼字符串，会持续产生托管分配。对象池能减少反复创建，但池里的对象、Mesh、图集和材质仍占内存。一个场景反复进出后，看峰值和释放后的基线，才能知道有没有留住上一局的东西。

成本看什么RevGame 的做法
托管分配有效 GC.Alloc、收集所在帧复用候选容器、反馈队列、空闲对象和稳定委托，文字在数值变更后更新。
原生驻留纹理、Mesh、字体和音频常驻字节预分配有上限的网格。回池清绘制范围，真正销毁时销毁独占的 Mesh。
加载峰值冷启动耗时、切场前后峰值及引用在对应流程预热必要资源。迟到回调核对代次，归还临时租约与旧场景引用。

一次租用由 RevScope 管局次，RevPool 管对象，RevResManager 管资源引用。归还前先使旧回调失效，再清 Tween、事件、材质参数和本局数据。下一位租用者拿到干净对象。用一笔已知分配校验计数器，再报告稳定期分配。 池与加载租约 · 分配、驻留与慢帧样本

PRACTICE / 06

按实际使用范围组织资源包

图集把小图放进较少纹理页，常能减少纹理切换。AB 是资源的发布与加载单元。项目按使用场景和寿命归属 Sprite Atlas V2 和包，其他模块通过依赖共享同一份资源。这样玩家打开一个页面时，只需要预载当前用途的图集和依赖。

备用 UI 的实测。把备用图混进常用图集时，同根纹理原生内存从 9,009,968 B 增到 9,840,612 B。把备用图拆到独立图集后降到 7,219,172 B，较原来少约 19.9%。因此容量、加载时机和释放引用要一起看。鸦鸦表情后来也按 Gal、对战和其他业务使用范围分包预载。 固定资源根的图集对比 · 表情图集拆分实现

源图压缩先影响文件大小和下载。加载到 Unity 后，纹理的原生占用主要看导入后的平台格式、尺寸、Mip 和实际页数。PC 与 Android 分开查。自定义 Shader 采样也要在真实 AB 验收 UV、透明边缘和图集延迟绑定。 Unity 纹理平台导入设置

同平台下按真实入口查图集唯一归属、依赖包和源图重复打包。清空场景后再按资源引用核对释放。读图集的效果着色器要区分原图局部 UV 与图集页 UV，以免扭曲采到邻图。 图集绑定与生命周期

PRACTICE / 07

让 UI 与战斗反馈按变化刷新

血条位置需要跟随运动，比例只在 HP 变化时更新。文本刷新可能重建字形或引发布局计算。相机的基础棋盘布局可由安全区、尺寸和宽高比缓存，再叠加当帧震屏和 Boss 特写。输入命中、字幕和真实伤害回执仍走原入口。

弹道、飘字和短效先读已经发生的战斗回执，再按项目预算呈现。设定上限时明确超量的合并或优先级。复用池对象仍要恢复颜色、位置、时钟和监听器。调合批或拆 Canvas 时，检查实际重建、提交和透明顺序。RevGame 曾试过额外的子 Canvas，实测净收益不稳定后恢复原布局。 密集反馈与子 Canvas 对照 · 布局计算源码

PRACTICE / 08

给自己的改动做一次对照

  1. 写清基线。记版本、平台、画质、分辨率、VSync、目标 FPS、场景、种子、人数、技能触发和实际攻击数。预热和采样分开。
  2. 只改能归因的一段。选择真实入口标记 CPU 规则、提交或其他热点。看 GPU 有效样本、内存和缓存失效成本。优先在同进程交替跑几轮，保存升降和异常。
  3. 验证游戏照常运行。核对同一逻辑时刻的实体、命中、随机序列和结果。看同一画面的动画、排序、字体、资源冷启动，并验证暂停、恢复、回池或退出。
  4. 按指标交付。CPU、GPU、整帧、上传量和内存逐项汇报，区分局部与整场。先用测试回执给出实际结果。用户明确要求时再按指定路径输出文件报告，临时工单在消费后删除。

可以直接交给 AI 的任务描述

用 $revolution-performance 审查这次改动。先说明每帧、每逻辑步和数据变化时各做哪些工作，核对 CPU、GPU、内存和缓存。固定输入和画质做前后对照，检查规则结果、视觉、暂停和退局回收。对话给出实测、代价和未覆盖设备。
