DECISION / 01

结论与取舍

你的判断成立，而且比"用不到同步"更进一步：围棋连"服务端裁决"都不需要。理由是三条硬性质：

  • 确定性：规则里没有任何随机与物理，给同样的输入必然得到同样的输出。
  • 状态可重建：一串落子坐标就能还原唯一棋面，不需要传快照。
  • 输入稀疏：一局 200 手、10 分钟，服务端只做转发，负载可忽略。

所以服务端剩下的职责只有三件：配对、转发、感知断线。原来那套"服务端权威 + 幂等校验 + 时钟裁决"整套都可以删掉。

但有一个东西不能一起删：接收方校验。它和反作弊不是一回事—— 反作弊是防"蓄意作弊的人"，接收方校验是防"对方客户端的一个 bug 把我这边搞崩"。 收到落子后仍然要用同一份内核试算一次，非法就拒绝并请求重同步。这层是健壮性，不是安全。

1.1 这个决定换来什么

少做的省下的
服务端规则计算不用在服务端跑 GoRules，不用维护一份服务端内核对拍
防作弊与反外挂不用做行为分析、异常检测、封号流程
时钟权威不用处理"服务端时钟与客户端时钟偏差"的一堆边界
幂等与重放保护只保留"接收方丢弃重复 seq"，不做服务端账本

1.2 这个决定要求什么

代价集中在一处：两端的内核必须完全同源。以前双端不一致还有服务端兜底，现在没有兜底了， 不一致就会直接表现为"两边棋面不一样"。所以第 06 节的对拍测试从"建议"变成必须做。

REJECT / 02

为什么不用帧同步和状态同步

方案它解决什么问题放到围棋里会怎样结论
帧同步（Lockstep）大量单位连续运动、每帧输入要对齐，如 RTS、格斗要求每帧采样输入并保证双端逐位一致；围棋几秒才有一个输入，99.9% 的帧是空转，带宽与确定性成本全是白付否决
状态同步（周期快照）状态复杂且频繁变化，如 MMO 的位置、血量棋面本来就是离散的，一手只改 1~19 个格；周期快照反而引入快照与落子交错的乱序问题，丢一个包就要全量重发否决
服务端权威 + 客户端预测防作弊、需要第三方裁定本期不做反作弊，等于多写一套服务端内核 + 幂等账本 + 时钟裁决，收益为零本期不做
纯 P2P没有服务器成本NAT 穿透、暴露 IP、掉线无感知，成本比转发更高否决
客户端权威 + 服务端转发回合制、离散状态、不需要防作弊落子方本地即生效，对手收到后自己重算，服务端一条消息转发完事采用

围棋有几个特性决定了它天生适合事件驱动。这些同时也是"以后要不要改联机方案"的判断依据：

  • 状态是离散的：81 个格子，每格三种取值，没有任何连续量，不存在插值需求。
  • 输入是稀疏的：一局 200 手、10 分钟，平均 3 秒一次输入。
  • 没有物理与随机：除贴目常数外没有随机性，不存在"双端算不一样"的风险。
PROBLEM / 03

真正要解决的问题

去掉服务端权威之后，需要解决的问题从"四个大件"缩到五条具体的事，全部围绕"两端看到同一个棋面"：

问题不做会怎样做法
消息顺序与去重乱序或重发导致多下一手、棋面错乱每方 seq 单调递增；接收方按 seq 丢弃重复、发现缺口即请求重同步
接收方校验对方一个 bug 或非法手把我这边搞崩收到后用同一份 GoCore 试算，非法则不落子并请求全量序列（健壮性，不是反作弊）
两端内核同源两边规则不同，棋面直接分歧，且没有第三方能纠正同一份源码 + 协议带版本号硬拦 + EditMode 对拍测试（见 06.3）
断线重连切后台回来一片空白，只能弃局本地存 MoveList，重放即可；缺口向对手或服务端补
时间显示与超时两边倒计时数字不一样，看着像卡了开局广播一次时间戳，各自用本地时钟算；落子带 elapsedMs 让对手校正

接收方校验的具体做法：收到 G2C_GoOpponentMove 后，用自己的 GoCore 试算这一手。 合法就落下并播放动画；非法就不落子，向对手请求一次全量序列重同步，并在界面上提示"对手数据异常，已重新同步"。 整个过程不弹错、不闪退、不卡死。

MAPPING / 04

Fantasy 结构映射

因为没有服务端计算，这套映射比"服务端权威"版本薄了一层：房间不再需要一个"裁判循环"，只需要能拿到双方的 Session。

职责Fantasy 机制关键 API说明
登录、大厅、匹配队列Root Scene（配置在 Fantasy.config）—常驻，进程启动时创建
单局房间（只配对与转发）SubSceneScene.CreateSubScene(parent, SceneType.GoRoom)一局一个，Close() 即清空该房间全部实体
落子转发客户端消息 HandlerMessageRPC<C2G_GoMove, G2C_GoMoveResult>Handler 里取对手 Session 直接 Send，不做规则计算
断线感知Session 断开事件Session 的 Disconnect 回调通知房间另一方，并保留 90 秒重连窗口
对局记录（可选）MongoDBISupportedSerialize、scene.World.Database转发时顺手存序列；便于排查，不承担判定职责
多机部署ServiceDiscovery—房间少时单机即可，M4 之后再考虑

4.1 连 Roaming 也不需要

Roaming（SessionRoamingComponent）解决的是玩家在多个后端服之间迁移，消息要跟着人走。 围棋一局两人、10–15 分钟、玩家不会在对局中途跑去别的服，而且服务端本来就不算东西——没有状态需要跟着人迁移。

做法：Session 连到 Map 服，房间 SubScene 里直接持有两个 Session 引用，落子 Handler 里调到对手的 Session 上 Send 即可。 一条消息一跳，没有路由表、没有 Address 解析、没有 Terminus 生命周期。

4.2 房间代码骨架

整个房间逻辑大概就这么长。注意 Handler 里没有一行规则计算：

// 房间只做两件事：记下两个人、把一方的落子转给另一方
sealed class GoRoomComponent : Entity
{
    public long RoomId;
    public long BlackUid;
    public long WhiteUid;
    public Session BlackSession;
    public Session WhiteSession;
    public readonly List<GoMove> MoveList = new();   // 顺手留一份，便于复盘与重连
}

// 落子 Handler：不做任何规则计算，只转发
public sealed class C2G_GoMoveHandler : MessageRPC<C2G_GoMove, G2C_GoMoveResult>
{
    protected override async FTask Run(Session session, C2G_GoMove request, G2C_GoMoveResult response, Action reply)
    {
        var room = session.GetComponent<GoSessionComponent>().Room;
        var target = request.Side == GoSide.Black ? room.WhiteSession : room.BlackSession;

        room.MoveList.Add(new GoMove { Seq = request.Seq, X = request.X, Y = request.Y, Side = request.Side });
        target.Send(new G2C_GoOpponentMove { Seq = request.Seq, X = request.X, Y = request.Y, Side = request.Side });

        reply();
        await FTask.CompletedTask;
    }
}
CORE / 05

落子序列即真源

服务端不算规则之后，这条设计反而更重要了——因为序列变成唯一的现场记录：

棋面是派生数据，序列是原始数据。客户端的棋面随时可以由本地的 MoveList 重放出来； 服务端顺手也留一份（转发时顺手 append，成本为零），但不依赖它——它是便利，不是权威。

为什么两端各存一份而不是集中存：

  • 重连：自己本地就有序列，重连后直接重放，甚至不需要问服务端。
  • 复盘：序列回放即录像，不需要额外存中间帧。
  • 分歧兜底：万一两边棋面不一致，对比双方序列的第一处差异就能定位到具体哪一手出的问题。
  • 观战：新观众从起始重放到当前手即可。

服务端那份副本的用途是"双方都掉线时留给对局一个记录"，以及便于排查问题，不承担判定职责。

KERNEL / 06

规则内核：GoCore 是唯一的裁判

这一节原本是"服务端与客户端要共用内核"，现在变成更硬的约束：客户端 A 与客户端 B 必须共用内核， 因为没有任何第三方能纠正分歧。

6.1 现有实现不能复用

现有 BoardModel 与 GoRules 是变体棋（大棋 + 加气 + 攻击），语义不同，不能拿来下正经围棋：

现有实现为什么不能用于正经围棋
Piece.Size 支持 1×1 / 2×2 / 3×3围棋棋子永远是单点，多格棋子的连通、气、边界算法全部不适用
BonusLiberties 加气围棋的气是纯几何结果，可加气等于改了规则
IsEyeGarrison / HasEyeGuardAura变体玩法的眼防护机制，围棋里不存在
依赖 UnityEngine 与 MonoBehaviour 视图纯逻辑内核不该有 UI 与场景依赖，也没法做无头自对弈测试
每格一个 Cell、每子一个 Piece 对象自对弈与批量校验要跑几万次，对象分配成本高

6.2 GoCore 的设计约束

  • 纯逻辑：netstandard2.1，不引用 UnityEngine，客户端与服务端都能编（服务端虽然不算规则，但工具与测试要用）。
  • 扁平存储：byte[81]（0 空 / 1 黑 / 2 白），不建对象图。连通块用可复用的 int[] 栈做 flood fill，单次落子零分配。
  • 超级劫用 Zobrist：每格每种颜色一个随机数，局面哈希 = 异或；本地维护 HashSet<ulong> 存历史哈希，落子前查重。
  • 单一入口：TryPlay(x, y, out PlayResult)，返回是否合法、提了哪些子、是否成劫、是否终局。不提供"只校验不落下"的旁路，避免自己这边状态漂移。
  • 确定性：同样的输入序列必须得到同样的输出，禁止使用 Random、DateTime.Now、字典遍历顺序等不稳定输入。

6.3 双端同源怎么保证

没有服务端兜底之后，这一节是全案最该投入的地方。三种做法：

做法优点缺点建议
单一源码目录 + 两端引用物理上只有一份，不可能改歪Unity 的 asmdef 要指向项目外目录，需确认编译顺序采用
编成 dll 双端引用版本清晰每次改动要重编 dll，Unity 侧还要处理 .meta备选
两边各写一份各自舒服必然漂移，且没有服务端兜底，漂移会直接变成对局事故禁止

三道保险，缺一不可： ① 协议带内核版本号，开局前比对，不一致直接拒绝开局并提示升级——这是最省的兜底； ② EditMode 对拍测试，同一批随机序列跑两遍断言棋面哈希一致； ③ 对局中轻量对账，每 20 手附带一次局面哈希，不一致就触发重同步。前两条必做，第三条可选但便宜。

PROTOCOL / 07

协议清单

去掉服务端校验后，消息从"请求-裁决-广播"退化成"请求-转发"。消息数量少了三分之一：

消息方向字段说明
C2G_GoEnterC → SroomId, token进入房间；token 由匹配结果下发
G2C_GoStartS → C（双方）blackUid, whiteUid, mySide, komi, coreVersion, startUtcMs开局；coreVersion 不一致直接拒绝开局
C2G_GoMoveC → Sseq, x, y, side, elapsedMs落子方本地已生效，发出去只是通知
G2C_GoOpponentMoveS → C（仅对手）seq, x, y, side, elapsedMs原样转发，服务端不校验规则
C2G_GoResyncC → SfromSeq发现缺口或非法手时请求补发
G2C_GoResyncS → CmoveList[], fromSeq服务端副本补发；没有副本则转给对手代发
G2C_GoOpponentLeftS → Creason对手掉线 / 认输 / 超时，只通知不裁决
G2C_GoEndC → S → Cresult, territory, komi, reason由结束方算出结果，服务端只转发；双方各自显示
FLOW / 08

一次落子的完整链路

  1. 落子方本地试算用本地 GoCore 跑 TryPlay，非法则当场拦下并提示原因，不发请求。此刻本地就是权威。
  2. 本地立即生效落子动画与棋面同时更新，没有"待确认"状态——不需要等服务端回话。
  3. 发送 C2G_GoMove{seq, x, y, side}，不等应答（fire-and-forget），失败由重发兜底。
  4. 服务端转发记 seq 与落子，原样转给对手的 Session，不计算、不校验规则。
  5. 对手接收用同一份 GoCore 试算这一手。
  6. 合法则落下播放动画，棋面推进到同一状态。
  7. 非法则不落子，发 C2G_GoResync 请求全量序列，界面提示"已重新同步"，不弹错。
  8. 对手超时未收到则本地记一笔，下一手到达时按 seq 判断是否缺手，缺则重同步。

延迟体验：落子方是零延迟（本地即生效），对手是"一个消息往返"。 同城时约 30–60ms，棋类完全够用。不需要客户端预测——预测的前提是"服务端可能否决我"，现在不存在这种情况。

HINT / 09

落子建议放在哪

服务端已经不算规则了，再让它算建议也不合适——它连棋面都没有。所以建议放客户端：

方案延迟能否限制次数成本结论
客户端本地算< 1ms只能自律，可被改零采用
服务端算一个往返能强约束要让服务端也维护棋面，与不算规则的决定冲突本期不做

评分项（权重可配，M1 之后按对局数据调）：

  • 提子价值：这一手能提的子数；能救回自己被叫吃的块同样加分。
  • 气的变化：落子后己方块气数增加、敌方块气数减少。
  • 角与边：9 路盘角部价值高，开局优先推荐空角与星位附近。
  • 连接与切断：能连上自己的孤棋，或切断对方两块。
  • 做眼：这一手能形成真眼时额外加分。

两件必须写在界面上的事： ① 建议基于启发式评分，不是必胜下法；
② 每局 3 次的限制是客户端自律，改客户端可以绕过——我们不校验，也不追究。

CAPACITY / 10

容量估算

服务端只转发，成本比"权威"版本低一个量级：

项数值说明
单次落子转发约 60 字节seq + 坐标 + 时长，服务端只搬运
服务端单步开销微秒级不跑规则，只做序列 append 与 Session 转发
单局序列约 200 条 / 4KB两端各存一份，服务端可选存一份
1000 并发房间约 333 手/秒转发单核远未饱和
SubScene 创建开销毫秒级共享父 Scene 的对象池与定时器
对局记录存储10 万局约 2–5GBMongoDB，按 roomId 建索引

结论：性能完全不是问题。真正的瓶颈只剩匹配池冷启动（人少时匹配不到人）， 所以策划案的数值表里给了"匹配 60 秒转人机"的兜底。

RESILIENCE / 11

断线重连与超时

11.1 重连

没有服务端权威之后，重连反而更简单——本地就有完整序列：

  • 短暂断网（切后台、地铁）：本地 MoveList 完整，重连后直接继续，连同步都不需要，只补收断线期间对手的落子。
  • 客户端重启：本地存档里存了 roomId + MoveList，启动后重放并请求服务端补发缺口。
  • 两边序列对不上：比对第一处差异，以落子方的序列为准重同步（因为他本地立即生效，他的序列必然包含他自己那一手）。
  • 超过 90 秒未回来，判该方认输。

11.2 超时

没有服务端时钟，超时只能靠两端各自计时。这在围棋里完全可行，因为读秒精度是 30 秒级，几百毫秒的差异无所谓：

  • 开局时服务端广播一次 startUtcMs（只是时间戳，不是裁决）；两端各自用本地时钟算流逝。
  • 每手落子带一个 elapsedMs（落子方自己报的思考时长），对手据此更新自己的显示，避免两边数字跳。
  • 超时判定：等待方在本地计时到 0 后，宣布"对方超时"并结束对局。
  • 争议可能性：如果一方故意报小 elapsedMs 拖时间，对手会先判他超时——所以这个字段被对手监督，比服务端权威版更容易作弊的空间其实不大。

掉线不暂停时钟。暂停会被用来拖时间。90 秒重连窗口已经能覆盖手机切后台。

TRADEOFF / 12

放弃了什么

这一节是给评审和未来的自己看的。选择客户端权威就等于放弃了下面这些东西，写成清单，避免以后有人以为这是"没做完"：

放弃的东西后果接受的理由
防作弊改客户端可以下非法手、无限提示、伪造思考时长只做好友局与休闲对战，不设赌注、不做实物奖励
排位公信力段位只对本机有意义，可以刷段位定位为自我参考，不做官方榜
争议裁定双方各执一词时没有第三方判好友局，冲突线下解决
服务端权威序列服务端那份副本可能缺手（断线时）以落子方本地序列为准，冲突时重同步
跨设备续局换手机后本地序列丢失，无法续下本期内不做；若要支持，改为服务端存序列并允许拉取

12.1 如果以后要开排位

只要出现"排名有公信力"的需求，服务端权威这一层就必须补回来，而且是从协议层重做，不是加个开关。 到那一步需要的东西文档里都留着：服务端 GoCore 同源编译、seq 幂等账本、服务端时钟裁决。 好消息是 MoveList 即真源的设计让迁移很平滑——搬序列，不搬状态。

12.2 被否决的同步方案

  • 帧同步：输入稀疏、无连续量，确定性与带宽成本全是白付。
  • 状态同步：周期快照会引入乱序与全量重发，反而更复杂。
  • Roaming 跨服迁移：一局两人、10 分钟，没有迁移场景，也没有状态要迁移。
  • 纯 P2P：连"消息中转"都省了，但 NAT 穿透、双方互相暴露 IP、掉线无感知，成本比转发更高。
  • 服务端权威反作弊：本期明确不做，见第 12 节。
