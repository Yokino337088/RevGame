1. 当前项目走到哪一步

当前已经有一套可在 Unity 编辑器里从主界面玩到战斗、结算和章节奖励的完整原型。 玩法服务、局外流程、界面、资源、池化表现、音频、Excel 导表和 GM 验收均有实际接线，并非只有静态界面。

目前适合把它称为“框架业务验证原型”。正式生命/攻击和敌方阵容仍为占位，轻松获胜依赖明确的辅助机制，持久存档和真机发布链路也没有完成。因此，流程能走通与战斗已经好玩、数值已经合理、手机已经可以发布，是不同层次的结论。

判断维度 当前状态 可以据此得出的结论
编辑器内玩法闭环 已完成 主界面→选关→六牌布阵→自动战斗→结算→下一回合/章节奖励可以串起来。
Revolution 业务接入 已完成 公开门面可以支撑本原型；已用到流程、作用域、服务、UI、资源、池、计时器、事件、声音、导表和 GM。
战斗观感与操作 部分完成 已有低频移动、伤害/攻击/升级弹幕、翻牌和手机横屏布局，仍需调整战斗长度与敌方策略。
正式内容与平衡 部分完成 有六章结构与占位配置，但不能等同于六章手工设计、连续平衡通关或正式数值完成。
手机发布准备 未完成 目前以编辑器直读资源和 Simulator 验证为主，尚无 Android/iOS 真机、AB 及小游戏验收结论。

“已完成”均指本文写明的原型范围；“部分完成”表示有可运行基础，但缺关键内容或验证；“未完成”表示还没有交付该能力。

2. 今天的两轮 UI 修复

2.1 第一轮：六牌拉开列距，修复手机右侧留空

六张手牌继续放在左侧，两列三行。此前横向与纵向共用较小间距，虽然卡槽没有直接重叠，视觉上仍然挤在一起。现在新增 GameBattleLayout.HandCard，让实际 UI 与布局检查使用同一份卡槽计算。

水平列间距取“左栏宽度的 16%”与“安全区高度的 6%”中较小值，纵向间距仍为安全区高度的 1.2%。卡片尺寸同时受两列总宽和三行总高约束，先给间隙留位置，再决定牌能做多大。这样既能在宽横屏上拉开两列，也能在较窄横屏上留在手牌区域内。

右侧深灰条的原因已经通过 Unity MCP 量测：Note20Ultra 模拟设备物理尺寸为 3088×1440，非全屏时 SimulatorInsets=(0,0,0,168)，实际游戏渲染区域只剩 2920×1440。原因是上轮验收使用 SetResolution(..., false) 后保留了系统导航栏区域；背景图片和等比覆盖算法本身正常。

启动修复放在 GameBootstrap.Awake：Android/Editor 下通过 UnityEngine.Device.Screen.fullScreen = true 明确全屏。同时，经 Unity MCP 使用 SetResolution(0, 0, FullScreenMode.FullScreenWindow) 恢复模拟设备默认全屏状态，业务入口本身不调用 SetResolution。背景继续使用指定图片覆盖渲染区，交互继续通过安全区避让刘海。后续验收临时改分辨率也必须保持全屏，并在 finally 中恢复约定的设备与预览状态，避免测试结束后影响人工游玩。

这一轮已执行 737 条布局检查，并在 3088×1440、1920×1080 的 Play 画面确认背景铺到右边缘。最终量测为全屏、四侧 Insets 均为 0、六个卡槽活动、翻牌结束后缩放与旋转复原，场景为 1 个相机和 1 个 Canvas。具体证据范围见第 7 节。

2.2 第二轮：文字更醒目，并统一布局设计基准

本轮已经把 UI 统一为实际粗笔画中文字体、粗体样式与居中对齐，并提高文字的明暗对比。通过 Unity MCP 导入 NotoSansCJKsc-Bold.otf（17,002,248 字节），SIL OFL 1.1 许可和来源说明一并保存在 Assets/ArtRes/字体。这次替换了细衬线字形，不只是勾选原字体的 Bold。

字体入口 GameAssetBuilder.Font() 改为统一读取新字体，Label() 默认设置 Bold；GameArtMigration.ApplyTypography() 经 MCP 保存了 49 个 Text 节点，覆盖 7 个 UI 预制体及 1 个 BattleEventNotice，包含六槽子节点与隐藏文字。常规文字采用 Bold/MiddleCenter：浅底使用近黑 #0E0A06，深底使用暖白 #FFFAEB，配合 0.45 或 0.8 的细描边。按钮字号 32、结算详情 28、计数 30。Notice 标题运行时继续保留 Excel 的语义色，并使用黑边与粗体，不把全部事件标题强制刷成同一种颜色。

CardItem 的属性文字改为“生命/攻击”两行，独占底部高度；肖像向上避让，避免图片挤到属性。运行时自动适配的牌名字号上限改为 24、属性上限 20、最小字号 14，避免资产上调后又被旧运行时上限缩回小字。

GameBattleLayout.DesignResolution 明确为 1920×1080，启动入口显式把它赋给 RevUISetting.ReferenceResolution；实际根 Canvas 原本也使用 1920×1080。这里统一的是横屏 UI 设计基准，业务代码不调用 SetResolution 强改手机物理渲染分辨率。唯一的编辑器预览已通过 MCP 固定为 Game 中的“RevGame 1920x1080”，本轮后续截图只使用这一实际预览，不再切换其他实际测试分辨率。

本轮编译未发现 error CS，重新执行 GameLayoutChecks.Run()，737 条再次通过。该检查在内存中计算多尺寸的几何结果，不改变当前 1920×1080 预览。资产逐项审计确认 49 个 Text 均使用 NotoSansCJKsc-Bold、Bold、MiddleCenter 和 Outline，失败 0；8 个界面/提示的 70 个 Sprite 引用中，旧 UI 引用为 0。

在唯一 1920×1080 Game 预览实际截图并目视检查 Home、LevelSelect、Prepare 六牌、Settle、Reward 与战斗 HUD，文字清晰，没有互相遮挡或截断。五张界面截图保存在 Temp/UiTypography/Verification/{home,levels,prepare,settle,reward}-1920.png；这是忽略目录中的本机验收材料，不随 Git 提交，也不是实体手机验收。编辑器迁移后的规则 570、布局 737、Play 回合表现 136，以及池化动画复用均已本轮重跑通过，详见第 7 节。

今天没有实施下一版战斗难度、敌方眼阵或 AI 改造。第 8、9 节全部是明天的方案与候选参数，当前游戏仍使用第 3 节所列节奏与辅助机制。

2.3 编辑器目录迁移与 GitHub 交付要求

按用户追加的目录要求，原 Assets/GameScripts/Editor 整体通过 Unity MCP 迁到 Assets/Editor/RevGame，共 9 个 C# 文件，GameScripts 不再存放这批编辑器工具。迁移保留原目录及文件的 .meta GUID，RevGame.Editor 命名空间及公开 API 不变，原有 GM/MCP 调用名称无需跟着目录改名。

Unity 将 Editor 特殊目录中的脚本作为编辑器代码编译。此次迁移前后都在 Editor 目录内，且没有新增或调整 asmdef，因此仍属于 Assembly-CSharp-Editor；只是把文件放到项目约定的统一位置，没有改变运行时与编辑器的程序集边界。资源引用依赖 GUID 而不是这一层物理目录名，保留 meta 可避免移动时打断已有引用。

迁移后已通过 Unity MCP 重新执行规则 570 条、布局 737 条及 Play 回合表现 136 条，均通过；池化检查和实际 1920×1080 UI 也已重新验收。这样有此次迁移后的实际证据，不只是沿用迁移前的历史数量。验收范围仍是本机 Unity 编辑器，不扩展为实体手机或连续六章平衡结论。

用户同时要求将今天产出推送 GitHub。本报告随今日提交交付至 origin/main，最终提交号与推送结果见本次交付消息；文档不预写尚未发生的远端成功结果。Temp 验收截图不随提交交付。

3. 当前已实现的功能清单

以下包含前序实现和今日修复，不能全部理解为今天新增。数值是当前源码中的原型配置。

模块 玩家现在可以看到或操作的行为 关键边界
主界面与选关 从主界面进入六章选关，未解锁章节不可进入，战斗中可返回主界面。 章节解锁只保留在本次程序运行内。
回合结构 六章，每章 10 个普通回合与 1 个 Boss 回合，共 66 个配置入口。普通回合结算后继续，Boss 胜利后进入章节推进。 66 个入口不是 66 个独立手工关卡，也不是已连续通关验收。
拼格棋盘 9×9、81 个独立格子，格边长 1.15；图像、高亮、点击区和大棋占格使用同一套坐标。 使用独立格子，未恢复整张错位棋盘图。
全盘落子 准备期可在任意空格下己方棋子；普通棋不能覆盖已有棋子，大棋必须整块放得下。 “空格可下”仍需满足整块身体占格规则，不是允许大棋身体越界。
免费重摆 准备期点击己方棋子选中，再点空格调整位置，不消耗手牌与落子额度。 准备、战斗等阶段有明确操作门禁。
六张手牌 首回合、后续普通/Boss 回合、重开及奖励后统一发满六张；每回合最多六次正常落子。 不继承上一回合只剩一张的数量；奖励牌占六个槽位中的一个。
剩余牌刷新 剩余 N 张就重抽 N 张，保留各牌星级，不补落子额度，不改棋盘。旧牌编号失效。 不是每次刷新无条件补回六张，也不是免费追加可下牌数。
翻牌交互 六个常驻 CardItem 复用；DOTween 错峰翻转，到侧面后换内容；动画期间锁定刷新和准备。 换轮、关闭和中断主动复原，防止带着旧旋转进入下一轮。
棋子图鉴 剑士、盾战、重剑、弓箭手、重弩、水法师、火法师、牧师、刺客，共九种、每种三星定义。 生命和攻击基础值仍是原型占位，不代表正式职业技能全部完成。
星级与合成 三个同名同星合成；我方 3★默认占 2×2，敌方普通 3★默认仍占 1×1，Boss 显式指定 2×2/3×3。先验证空间，再消费材料；空间不足时保留材料。 成眼棋群不作为自动合成材料，升星继承材料总体血量比例，不直接全满。
气、连通块和眼 同阵营连通块统一计算公共气、眼、叫吃和锁死；共用一口气只算一次，边角眼按棋盘内相邻格计算。 采用当前项目的局部围眼规则，并非完整围棋规则系统。
围棋状态效果 锁死不能行动且受双倍伤害；连通占格增加攻击、孤立受伤增加；有两眼的棋群每五秒回复最大生命的 5%。 两眼“活棋”是当前游戏中的阵型状态，不表示免疫一切战斗伤害。
职业加成 同职业达到 3/5 颗时逐档增加攻击；抽牌对己方已有职业有额外权重。 章节专属职业克制与完整职业技能拓展还没有做。
低频移动 我方自动战斗始终守阵；敌方只有攻击不到目标时，才每五秒最多靠近一次。普通滑步最多一格，保留马步合法性。 成眼棋子不自动走动；当前敌方不是能主动设计眼阵的策略 AI。
攻击节奏 普通行动周期 1.25 秒，服务与 Logic 以 0.3125 秒小步驱动。当前我方远程配置为两倍频率，约 0.625 秒一次。 行动进度决定出手，不依赖渲染帧率。
远程与目标 我方远程可原地跨盘锁定最近敌人，每次出手重新查目标；敌方已有弓箭手的两格直线攻击，以及火法师的炮型隔子直线攻击。 当前双方射程并不对称；明天是增加敌方远程配置与有效射界，不是从零新增远程能力。
Boss 战斗 Boss 主将带王冠、独立血条；后期有多颗大棋护卫，擒王结束战斗；普通回合 50 秒，Boss 不设普通超时。 默认轻松模式仍有 45 秒决胜辅助，不等于所有 Boss 已自然平衡。
回合胜负与残局 普通超时按双方剩余总血判定；同章连续回合保留己方残局与伤势，失败重开或进入新章清盘。 默认辅助通常会提前处理剩余敌人；底层超时规则存在不等于当前每局都会走到它。
章节奖励 Boss 后三选一：全队强化、同名牌、新棋子或符合条件的眼位石；选择后进入下一章。 “永久”强化指本次战役内，重新从选关开始会清局内强化；不写入磁盘。
第十回合选择 第 10 回合准备时可放弃该回合落子、直接进入 Boss，并取得攻击强化。 已经落牌就不能再跳过获取这份收益。
眼位石 满足当前开放条件后可通过奖励获得，在准备期补成合法眼；选牌、选棋子、选眼位石互斥。 不是随便点击就能在任意位置造眼，须经服务校验。
战斗事件 已接八种：天降援兵、回气、疗愈雨、连击、补眼、断链、守阵回气、炮火支援。无合法目标时有明确处理及日志。 当前自动轻松模式偏我方支援，尚未形成双方有来有回的事件体系。
轻松获胜辅助 最后一颗己方棋子至少保留 1 血；45 秒以真实支援伤害清除剩余敌人，HUD 明示辅助。首发事件 3.75 秒，之后间隔 5 秒，上限 12 次。 这是用户指定的保通关辅助，不能当作自然平衡与策略深度完成的依据。
攻击与伤害表现 棋子头顶攻击口号、飞行弹道、实际扣血数字，放大冲击、描边、上浮与淡出；顶排文字限制在可见范围。 伤害由服务先结算，弹道到达后显示数字；画面不会自行决定胜负。
棋子与状态表现 我方/敌方、棋种、星级读取对应图像与帧序列；显示血条、锁死标识、主将王冠和移动过渡。 平滑移动只改变图像位置，逻辑占格由服务/棋盘管理；回池停止 owner 动画计时器。
升级与增益 UI 升到 2★/3★及战斗事件都有独立 UI 文案与 DOTween 滑入、回弹、停留和淡出。每次显示最新一条。 短命提示使用独立区域，避免叠在手牌、棋盘或操作按钮上。
对象池优化 格子、棋子、短命弹幕、弹道与提示通过 RevPool 复用；各对象管理自己的 Tween。 回池 Kill(false)，不使用全局 KillAll；尚未做真机长期性能测量。
回合清场 准备、开战、结算边界清旧弹幕、提示、日志和延迟伤害；批次号拒绝迟到加载。棋盘加载与效果清理分开。 不等动画自然播放结束才换轮，暂停动画也必须回收。
横屏与美术 固定横屏，左手牌/中棋盘/右信息和操作；指定背景、英文新版 UI、结算与奖励指定底板；全屏修复已落地，UI 使用真实粗体中文字体与 1920×1080 设计基准。 UI 安全区与背景全屏覆盖承担不同职责。字体最终视觉/资产审计以第 2、7 节补充记录为准。
音频 RevSound 接入 BGM、落子、受击、升星、胜利与失败提示音，随流程播放和停止。 历史确认过播放状态和位置递增，未据此宣称音效审美或混音已验收。
Excel 配置 已用原框架导表生成弹幕文案、颜色、字号、时长、冲击倍率与远程频率的数据和 C#。 当前不是全部战斗数值都已 Excel 化；正式血攻、敌阵仍待接入。
开发工具 GM 可选关、造局、落子、刷新、开战、触发事件、返回首页；编辑器工具装配资产、检查规则/布局/回合清理/池化。 工具会调用真实服务并返回 Success/Message，不把工具调用成功当作业务成功。

对应主要证据：前序实现报告、当前常量、战斗服务、成长与奖励、事件与辅助。

4. 代码从数据到画面的职责

4.1 先理解六层各自回答什么问题

可以把一次攻击理解为：“配置说这是什么棋子；模型记住它现在在哪、有多少血；服务判断这次能不能打并结算；流程决定什么时候推进；UI 和 View 把结果画出来。”面板和动画都不能反过来偷偷修改战斗规则。

层与入口 用新手能理解的话说明职责 主要文件
数据定义 相当于图鉴和关卡说明书，描述棋子种类、职业、星级、基础参数、奖励类型和事件名字。定义不会因为一颗棋子受伤而改变。 PieceCatalog、LevelCatalog、RewardDef、BattleEventCatalog。
运行模型与规则 记账本和规则尺：一颗 Piece 保存当前血量/坐标，BoardModel 保存每格是谁，HandModel 保存手牌编号；GoRules 计算气眼，MoveRules 只列出合法目标。 Piece、BoardModel、GoRules、HandModel、MoveRules。
业务服务 唯一裁判：检查阶段、牌、空格和额度；提交落子、刷新、攻击、奖励和胜负。失败返回原因，不先扣东西再发现不能做。 IBattleService、BattleService 及其 partial 分文件。
流程与驱动 相当于导演和节拍器：决定现在在首页、选关还是战斗；进入战斗开域，退出就收回这一段的逻辑；按固定小步让服务推进。 GameBootstrap、GameFlow、BattleLogic。
UI 与 View 相当于屏幕和演员：UI 处理按钮、文字与弹窗；View 把模型编号对应到格子、棋子、弹道和相机。接到事件后展示结果，不自己扣血。 PreparePanel、BattleHudPanel、BoardView、GamePresentation。
配置、池化与开发验证 配置把 Excel 变成运行数据；池负责反复借还短命对象；Editor/GM 提供复现和检查入口。 GameTextConfig、Generated、BattleEffectView、GameGmCommands、Assets/Editor/RevGame。

4.2 同一个 BattleService 为什么分成多个文件

partial 的意思是“同一个类分文件写”，不是同时运行多套战斗管理器。以下文件共同组成一个服务，界面通过同一个 IBattleService 接口发出请求。

文件 主要负责什么 后续修改时先找哪里
BattleService.cs 开回合、发牌、正常落子、固定步战斗、攻击、结算、敌方出生预检。 战斗节拍、目标攻击、敌阵提交、胜负。
BattleService.Placement.cs 准备期统一点击，区分选牌落子、选择己方棋子和免费换位。 触屏落子与调阵，避免和眼位石模式互抢操作。
BattleService.HandRefresh.cs 剩余牌重抽、提交新牌、读取远程行动频率。 刷牌规则；动画仅在 CardItem 中做。
BattleService.Progression.cs 开战役、推进回合、章节解锁、三选一奖励、职业加成、自动合成。 成长、奖励与“永久”的有效范围。
BattleService.Events.cs 八种支援、眼位石、统一伤害入口、最后一子保护及决胜辅助。 明天事件节奏和辅助收敛的主要入口。
BattleService.Diagnostics.cs 开发专用固定造局，快速复现合成、Boss、事件等场景。 为 AI、眼阵和极端盘面增加可重现夹具。
BattleService.*Checks.cs 开发环境规则断言，直接检查真实服务和数据。 加入不变量与失败场景验证，正式包不运行这些造局检查。

4.4 Excel、对象池与生命周期

工作簿为 战斗弹幕配置.xlsx。原框架 ExcelTool 把它导出为 Generated/BattleDataStructures.cs、Generated/BattleDataTables.cs 和 GameRes/Data 下两份数据。BattleText 当前 21 行，BattleTuning 当前 1 行。启动时用 RevTask 等待 RevDataTableManager.LoadAsync<T>()，验证必需内容后才进入首页。

“导出了弹幕表”不代表“所有数值都已导表”。基础血攻在 PieceCatalog，敌阵在 LevelCatalog，节拍等常量在 Consts，仍需后续按正式表替换来源。不要手改 Generated 和 Data 的导出结果。

RevPool 相当于可重复借还的道具仓库。借到一个弹幕对象时设置本次文字、颜色、位置并播放；播放完归还，下次复用。归还时必须 Kill(false) 并复原，不能触发上一轮的完成回调。BoardView 另有“整盘加载批次”和“短命效果批次”：清上一轮弹幕只推进后者，不能连 81 个棋盘格的加载一起取消。

HUD 的提示也要记录自己的批次。若旧异步加载在下一回合才完成，它只能回池，不能补播到新界面。计时器、事件监听、对象池与资源分组各有明确所有者；RevScope 负责域的回收，仍需配合对象自身的显式清理。

5. 新手理解三个完整流程

5.1 玩家点击一张牌，再点棋盘

  1. PreparePanel 只转发“选中哪张牌”的编号，不先在画面上生成一个假棋子。
  2. BattleService 检查当前是否准备期、牌是否仍在手里，以及选中的编号是否有效。
  3. 点击格子后，BoardModel 检查边界、已有占格及整块大棋是否能放下。
  4. 全部合法才一次性消费牌与额度、更新棋盘、刷新气眼并尝试合成。
  5. 服务发送事件，手牌槽重画，BoardView 才把真实棋子显示出来；失败则显示原因，原数据保留。

5.2 棋子发射弹道并打出伤害数字

  1. BattleLogic 按固定小步调用服务推进，服务累计每颗棋子的行动进度。
  2. 轮到出手时，MoveRules 提供合法敌人；BattleService 计算实际扣血，并发出攻击和受击快照。
  3. BoardView 从快照取当时位置，不依赖一个可能已经死亡或移动的对象引用。
  4. 从 RevPool 借出攻击口号和弹道，读取 Excel 文案与动画参数，用 DOTween 播放。
  5. 弹道到达后显示实际扣血；若期间已换回合，批次校验拒绝迟到弹幕。动画结束归还对象。

5.3 回合结算后进入下一轮

  1. 服务确定胜负，清手牌选中态，进入结算阶段；结算弹窗显示这一份结果。
  2. 场景表现归还弹幕/弹道，HUD 清旧提示和日志，取消延迟伤害，推进效果批次。
  3. 玩家点击继续，服务根据普通/Boss/章节状态决定下一步；失败返回明确原因。
  4. 开下一轮时重新发满六张。PreparePanel 枚举包括隐藏项在内的六槽，先清旧翻转，再绘制新牌。
  5. 同章按规则保留己方残局，换章清盘；奖励只允许消费一次。旧动画与异步回调不能把上一轮内容补回来。

8. 明天的战斗与 AI 改造方案

以下全部为计划，尚未实施；候选数值尚未定案。 目标是继续让玩家能够通关，同时让玩家有时间看清“敌方施压→我方受损→支援反击→重新稳住阵型”的过程。不能只靠堆血、无限增加弹幕或把普通棋全部加速。

8.1 先明确要保留的体验

  • 保留横屏、六张手牌、剩余牌刷新、全盘空位落子、准备期免费调阵。
  • 保留我方守阵和远程原地攻击，已有一眼/两眼阵型不因自动寻敌而散掉。
  • 保留“可通关”的目标，不能因为加入更多敌棋与敌方支援而让新玩家陷入必败。
  • 保留显眼的实际伤害、攻击、升级和事件提示，但控制同时出现数量，给玩家阅读时间。
  • 不擅自接入被策划砍掉的系统，不修改 Revolution 快照内核来实现业务 AI。

8.2 战斗时间与事件时间分开调

先测量当前各类局面“有效交战持续多久”和“哪种伤害过早清场”，再分别调整基础行动、敌人耐久、远程节奏和事件间隔。这里至少有四处不同的时间：敌人被消灭就提前结束的有效交战与普通 50 秒上限、45 秒决胜辅助、首次 3.75 秒/后续 5 秒的事件间隔，以及 Excel Duration 控制的提示停留。它们不能混成一个“战斗时长”参数。敌人在十几秒内被炮火清掉时，单纯延长回合上限没有用；延长提示停留也不会改变伤害与胜负。

建议让第一段交战先由棋子自身完成，之后再引入支援。一次事件先展示征兆和标题，执行效果，留出观察结果的时间，再允许下一次事件。若后续确认采用敌方增援或护盾等候选事件，必须有明显提示，并让玩家看得到应对窗口，避免无预警改变胜负；这类事件当前尚未定案。

普通回合、Boss、教学式早期回合应分开配置，不把所有难度塞在一组常量里。初期先用固定种子和少量代表场景调节，参数稳定后再扩至六章配置。

8.3 增加敌棋和远程，也要保证合法与可读

当前普通敌阵为 3～5 颗占位棋，已经会抽到弓箭手和火法师；它们有各自远程规则，但按空格扫描放置，并不主动构造战术阵型。明天计划增加敌方人数和远程占比、改进有效射界，区分前排承伤、守眼骨架、远程输出与必要机动棋，而不是简单把所有空格填满。

增加敌棋前先计算可用格，包括上一回合保留的玩家占格、玩家已围眼位、Boss 整块身体和计划保留的气。阵容需要先在临时计划中全部放得下，再一次性提交；失败则换较小合法模板或报告原因，不能偷偷少生成 Boss、把棋子生成到玩家身上，或破坏现有残局。

敌方远程增加后，要重新核对实际射程、直线阻挡和炮架条件。不要用“看起来是远程”代替“此位置确实能攻击”：否则它们仍会频繁移动，或整场站着打不到人。保眼远程站位应优先选择能开火又不挤掉眼与公共气的位置。

8.4 用真实气、眼规则预置或构造一眼/两眼阵型

第一版建议先做少量可读的阵容模板，再在合法空格中做平移、镜像或适合棋盘的旋转，控制复杂度。每个模板明确记录骨架棋、输出棋、预留眼位与必要气，而不是只保存几颗棋子的坐标。

计划的生成与验证顺序：

  1. 收集真实可用格和禁止覆盖区域，依据每颗棋子的身体大小预留全部占格。
  2. 尝试一眼/两眼模板及变换，眼位本身必须留空；边角模板按当前 GoRules 处理棋盘边界。
  3. 在临时棋盘摆好候选阵容，用现有 GoRules.Evaluate 重新计算连通块、公共气和眼数。模拟时复制模型快照，不把实时棋子引用直接放进临时棋盘，否则 Evaluate 会把试算结果写回当前战斗。
  4. 验证“目标眼属于预期敌方棋群、眼数达标、不是出生就锁死、关键远程有合法攻击条件”。不能只数空洞数量；两个空点必须按真实规则形成有效眼。
  5. 评分比较存活气、眼结构、远程输出位置与玩家距离。保留分数较高的合法候选；有次数上限，不能无限搜索卡住准备画面。
  6. 若没有达标方案，退回较简单但完整合法的阵容；让降级原因出现在开发日志和 GM 快照中，便于验收。

模板应优先复用 BoardModel、GoRules、MoveRules，业务算法放在现有 Data/Services 职责范围内。无需另起一套与真实规则不一致的“AI 专用棋盘”。

8.5 敌方行动先看守阵，再看攻击，最后才考虑移动

当前已经有“成眼不走、能打就打、攻击不到才低频靠近”的基础，明天在此之上细化决策。守眼骨架默认固定，远程只在没有合法攻击位置且不损伤阵型时考虑调整；机动棋承担必要的接近任务。

候选移动先验证完整占格，再用临时规则结果比较移动前后眼数和公共气。除非明确进入带提示的应急策略，不接受拆掉己方一眼/两眼、堵死己方最后公共气、填掉眼位的移动。距离相同时避免左右往返；攻速增益仍然不增加移动次数。

目标选择可以先做可解释的小规则，例如“可合法命中→能完成击杀→威胁较大的目标→距离/稳定编号”，而不急于引入复杂搜索。规则次序与具体权重仍待调试，不在文档中把它们写成已完成。

8.6 战斗事件有来有回，通关辅助做最后兜底

权威 v18 的现有约束是“事件只给增益，不出负面”。因此，先通过更合理的敌阵、攻防持续时间与我方支援节奏形成来回，沿用现有增益规则。把事件进一步分为敌方压力、我方应对和中性变化，是需要用户确认的候选设计，不是明天已获确认的实施项，也不能默认解除 v18 的边界。

若这项候选之后确认，再分别设置预算与冷却：敌方可短时加固或增援，我方通过回血、回气、补眼、援军或适量炮火回应；不引入不可应对的永久强化。用户未确认前，不增加敌方增益或对玩家的随机负面事件。

每类事件都要检查合法目标和可用空间，提示说明真实效果。没有合法目标时采用清楚、有限的替代效果，不能在已满的棋盘强塞援军，也不能为了表现而把眼位填掉。数值需要有上限和失效时机，换轮清理沿用已有批次/池化机制。

当前 45 秒决胜辅助会直接清除剩余敌人，容易盖过刚加入的阵型和事件。明天计划先把这个机制改为可观测的最后兜底：只有长时间僵持、己方确实无进展等条件满足才触发，并保留醒目的“辅助”说明；不要把强制清场当作默认每局的主玩法。

“最终可通关”仍是要保持的目标，但辅助的具体阈值、分级强度、Boss 处理和最终收尾方式尚未确定。调整必须覆盖弱阵、近战无法接敌、双方守眼和远程受阻场景，避免改完后出现无限对峙或失去通关保障。

10. 新同学接手操作与维护规则

  1. 打开工程 Assets/Scenes/SampleScene.unity，按 Play，从首页进入第一章；保持 Unity 编辑器打开。
  2. 左侧选牌，在空格落子；准备期点己方棋子再点空格可换位。刷新只重抽剩余牌；准备完毕进入自动战斗。
  3. 改弹幕文案/动画参数时编辑工作簿，使用 Revolution.Tools/配置表/导表工具；只改数值/文案用快速导出，改字段再全量导出。个人源位置在 UserSettings，换机器重新选表。
  4. 规则与 AI 改动先找 Services/Board/Battle，不先改 UI 动画来伪造结果；界面只转发动作和显示状态。
  5. 资产、导入、场景和预制体通过 Unity MCP 修改，源码按项目约定编辑；不要关闭 Unity 或重置用户已有改动。
  6. 非 Play 的规则/布局检查与 Play 的回合/池化检查分开执行。池化检查至少保持同一流程四秒，等待时不要切域或停止 Play。
  7. GM 先执行“RevGame/打开选关”，再“RevGame/进入战斗 1”；之后可刷新手牌、点棋盘、载入固定场景或开战。检查业务返回的 Success 和 Message。
  8. 当前编辑器唯一预览保留为 Game“RevGame 1920x1080”，字体修复后只在这个实际尺寸截图；几何检查可在内存计算其他尺寸，业务不调用 SetResolution 锁手机分辨率。将来独立验收若临时切实际渲染尺寸，必须保持全屏并用 finally 恢复约定的预览/设备状态，不能遗留导航栏或暂停动画。
  9. 注释使用中文，关键字段、接口、方法、算法与时序说明“为什么这样做、失败怎么办”，让新同学理解，不只把代码翻译成中文。控制流带大括号，参数签名不随意拆行。
  10. 业务只使用 Rev 门面；异步只用 RevTask；启动只初始化一次。Assets/Revolution 是框架快照，不在本项目顺手改内核；确需修框架先回源仓 main。
