# 功能完整性与缺陷闭环

Codex 等 Coding Agent 负责读需求和源码、判断缺陷、提出修法、修改工程与回归。RevMCP 执行测试计划并保存原始证据，RevCLI 操作编辑器。已有项目测试、当前工具注册表和玩家使用的正式入口优先复用。

## 从需求列出可证伪的用例

1. 从用户要求、项目 `AGENTS.md`、已确认的策划/设计和配置提取预期。源码用于找到写入和观测位置。需求不明或资料冲突时，记录影响判定的缺口，继续验证已有明确标准的部分。
2. 用稳定用例 ID 对应每项需求，写明来源、版本和环境、前置、真实入口、输入、精确后置、结束状态。按该功能涉及的路径选取下表各项。保存用例和测试计划，修复前后可按相同条件复跑。

| 需要覆盖的行为 | 可观测结果 |
|---|---|
| 主路径与需求中的替代路径 | 玩家入口可达，动作生效，业务状态、事件/回执和界面一致 |
| 边界与拒绝 | 空数据、上限、非法输入、重复提交或快速连点。核对拒绝原因，以及扣费、发奖、序号等相关状态的前后差值 |
| 异步与生命周期 | 加载、取消、超时、返回、重入或重连。等待真正就绪，核对旧回调、域、监听和引用是否泄漏到下一次 |
| 跨层交接 | 服务/模型、配置、资源、Prefab 绑定与 UI 对应。涉及 AB 首开、双端一致性或目标设备时使用相关真实环境 |

一次成功只覆盖该输入及其后置条件。明确要求的入口、规则、绑定或清理缺失时，用当前源码、配置或资产与可观察结果记录缺失。用例所需平台、资源模式、账号权限或测试数据缺失时说明缺口。没有证据的推测写在待验证项里。

## 执行与判定

- 从隔离前置开始。先发现实际注册入口，业务动作使用玩家共用入口，玩家交互使用真实指针/事件链。动作完成后读取业务状态。跨帧用只读能力等待稳定状态，`expect` 写确切值。需要测试拒绝时检查业务拒绝及状态保持。参照 [测试计划](plans.md)。
- 为复现保留实际输入、seed、账号/存档类型、平台、资源模式、代码版本及相关未提交差异。证据保留复现所需字段，凭据留在项目原有存储。用步骤 `id` 将断言映射到用例。失败以原始计划、`reportPath`、工单、日志或实际画面为证据。需要现场画面时在失败断言前采集，或在 `finally` 复位前做安全的只读观察。
- 核对 `steps`、`cleanup`、取消和新增错误。预检失败时业务计划尚未开始。已开始的计划遇到首个失败会跳过后续业务步骤，继续尝试 `finally`。漏跑用例记录为 `not_run`，前置允许时用独立计划补跑。清理失败先确认现场、恢复本轮状态，再继续变更。

| 用例状态 | 判定 |
|---|---|
| `pass` | 目标环境中已执行，有精确的预期与实测，相关后置成立 |
| `fail` | 在有效前置下证实业务、画面或生命周期违约 |
| `blocked` | 环境、注册、夹具、观测或中断使业务结果无法判定，保留原始错误 |
| `not_run` | 未执行，包括计划提前结束后跳过的步骤 |

`AssertionFailed` 先核对路径、预期和夹具，`ConditionTimeout` 先确认最后实测与运行健康。有效环境下稳定复现的完成超时也可能是业务缺陷。传输失联时先用同一工单或只读状态确认动作是否提交，再决定恢复方式。

## 定位、修改和回归

1. **锁定第一处偏差。** 对照预期和实测，沿“玩家/GM 入口 → Service/Logic → 状态写入或配置 → 回执/事件 → UI”阅读实际实现。把栈、业务状态或资产绑定与偏差对齐。找出触发条件、出错的所有者和违反的契约。用仓库相对 `文件:行号` 与符号记录证据。存在多种解释时，挑能区分它们的只读观察或最小复现。证据不足则保留假设。
2. **给出可实施的修法。** 写清在哪个责任层改什么条件、绑定或生命周期处理，哪些调用方或资源会受到影响，以及哪条断言能证明修复。收到旧缺陷报告时优先使用已有复现和 `code_refs`，核对目标版本、源码符号和证据。版本漂移或证据不足时补最小基线。业务缺陷落到项目源码，框架缺陷落到框架源仓库，按项目约定同步导出。
3. **在已授权范围内执行。** 实现后验收、修 Bug 或用户明确委托找出并修复时，落实证据支持的最小修改。保留首轮失败证据。纯测试、定位或建议任务在提交复现与建议后交付。阻塞项继续做可用的诊断。测试入口缺失时，在授权范围内补开发态只读查询、受控动作或复位，编译后重新发现。
4. **用原断言复测。** 最后一次影响 Unity 编译的改动后按 [编辑器技能](../../revolution-unity-editor/SKILL.md) 核对目标编辑器的本次重编工单。重新发现并按相同输入、模式、玩家入口和预期跑原失败用例，再按改动的共享调用方、拒绝副作用、取消/重入、资源或设备边界跑最小相关回归。测试工具或夹具有误时修测试并说明原业务覆盖缺口。只有新证据能指导下一轮时才继续调整，重跑保留首次失败与后续结果。

修复结案需要原失败用例通过、受影响的必要回归通过、相应编译/规范检查通过和清理复核。只有全数必要用例有有效证据、无未解决失败，才对本次范围写 `pass`。存在已证实未解决的失败时写 `fail`。必要用例、复测、编译或清理无法确认时写 `blocked` 并标明缺失。覆盖范围以本次用例为界。

## 可交接的记录

完整性审查、缺陷调查和修复回归，按项目证据约定保存一份 `defect-closure.json` 或等价的项目既有记录。HTML 摘要引用同一批用例、缺陷和证据。`rev_run` 的原始 JSON/HTML 由工具产生，这份记录由 Agent 根据实际结果填写，参照 [结构示例](../assets/defect-closure.example.json)。

- `target` 记录目标、环境与可复现实验参数。`cases` 用需求来源和步骤串起 `expected` 与前后 `observations`。每次观测注明源码版本/工作区、`status`、`actual`、原始 `evidence`。阻塞或未执行的实际结果留空并记录原因。
- `bugs` 关联已证实偏差的用例、影响、根因或待证假设、`code_refs`、修改建议、实际改动和当前状态。用 `cause_status` 标明根因已证实（`confirmed`）或待验证（`hypothesis`）。`code_refs` 指向能够解释偏差的具体源码/资产位置。未证实存在偏差的风险记录在 `unverified`。
- `checks` 保留编译、规范、新增日志、清理和相关回归证据。收到交接时用原始输入和证据继续推理，保留同一用例与缺陷 ID，便于比较前后结果。
