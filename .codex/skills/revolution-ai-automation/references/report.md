# 测试报告规范

报告是交付物，不是日志堆。判断标准只有一句：**别人不问你任何问题，也能看懂这次测了什么、结论是什么、凭什么。**

## 1. 命名：中文标题 + 日期

```
第一章流程自动化测试_2026-10-26.html
六章战斗性能压测报告_2026-10-25.html
```

- 标题用中文，说清"测的什么"；日期用 `YYYY-MM-DD`，取**数据产生那天**，不是改写那天。
- 同一天同一主题跑多轮，把轮次写进标题：`第一章流程自动化测试_第2轮_2026-10-26.html`。
- 不要 `report.html`、不要纯英文名、不要只有日期没有标题。
- 文件名里不能出现的字符会被自动替换成 `-`：`\ / : * ? " < > |`。

代码位置：`revautomation/report.py::report_file_name(title, day=None)`。`rev.py evidence`、`rev.py capture --report`、`rev_run` 都走这个函数。

## 2. 目录结构

```
文档/<主题>/
  <中文标题>_2026-10-25.html          ← 正文，就在这一层，一眼能找到
  <中文标题>_2026-10-25.md            ← 摘要（可选，给不看网页的人或 diff 用）
  <主题>_素材/
    画面/第1章_持续负载.jpg
    画面/第4章_连续战斗.gif
    证据/采样数据_2026-10-25.zip      ← 每轮 markers/status/逐帧 CSV 全在这一个包里
    证据/Profiler原始录制_2026-10-25.zip
```

- 报告放**顶层**，和同目录的其它文档并列；素材进子目录。
- 一次运行 = 一个证据包。不要把 `markers-1.txt`、`status.txt` 这类过程文件摊在目录里。
- 单文件超过 50MB 的原始录制单独命名、在正文里注明体积，别和其它东西混在一起。

## 3. 版式：沿用项目既有那套

不要每次重新设计。样式表来自 `revautomation/report.py::REPORT_CSS`；项目里已有同类文档时，以那份文档的样式为准（例如 RevGame 的《战斗性能优化规则.html》）。

| 设计变量 | 值 | 用途 |
|---|---|---|
| `--ink` | `#25352f` | 正文 |
| `--muted` | `#65736b` | 次要信息、图表说明 |
| `--green` | `#326956` | 主色：标题、强调、进度条 |
| `--gold` | `#a76e2d` | 警示、图注点缀 |
| `--paper` | `#f6f7f2` | 页面底色 |
| `--line` | `#dce3da` | 分割线、卡片边框 |

结构顺序（缺项可以合并，顺序不要打乱）：

1. `topbar`：品牌 + 本次主题标签。
2. `hero`：`eyebrow`（主题/日期）、一句话主张的 `h1`、`lead`、关键数字。
3. `metrics`：3 个数字，每个配一句口径说明。
4. 正文 `chapter` 卡片：结论 → 数据 → 热点 → 资源 → 验证 → 证据 → 下一步。
5. `footer`：证据路径、测试入口、未验证项。

## 4. 内容清单（缺一条就不算完成）

- **结论一句话**：能验收的和不能验收的分开写。`{success: true}` 不是结论。
- **断言明细**：每项需求 → 前置状态 → 玩家入口 → 后置断言 → 失败边界。数量要写实际跑的条数。
- **首个失败原因**：失败就写第一个失败的点，不要写"部分通过"。
- **环境**：工程、平台、构建模式（Editor / PC AB / Development Player / 真机）、分辨率。
- **测量口径**：每张表都要能回答"这个数怎么量出来的"，否则读者会把它当成别的意思（例如把 Editor 的 FPS 当手机帧率）。
- **图与 GIF**：见第 5 节。
- **未验证项**：明确列出没测的东西，不用"待优化"这类模糊说法。

## 5. 图与动图

- 截图至少三张：初始态、关键操作后、失败现场（没失败就放最终态）。
- 动态效果（技能、位移、粒子、UI 过渡）必须给 GIF；单帧看不出节奏。
- 体积按网页可用来定：截图转 **1600 宽 JPEG q86**（1920×1080 PNG 约 3MB → 约 300KB，文字仍可读）；动图 **≤720 宽**，10–20 帧，100–150ms 间隔。
- 只压体积：不裁剪、不拼接、不美化、不补画。正文注明"原图 1920×1080，这里换成 1600 宽 JPEG"，读者才知道自己看的是压缩版。
- 图片只证画面。数值结论必须来自断言与采样数据。

## 6. 证据收纳

- 每轮运行的 markers、status、逐帧 CSV、诊断 JSON → 合成 `证据/采样数据_<日期>.zip`，包内保留原来的子目录结构。
- 报告正文用相对链接指向这些包，不要指向已经删掉的散文件。
- 中间作废的采样（空 raw、暂停帧、被 Esc 中断的录制）不要塞进包冒充证据；要留就在正文里当成失败记录写清楚。

## 7. 反例（被明确要求重写过）

- `report.html` + `evidence/` 里 86 个散文件 + 6 张各 3MB 的 PNG：**看的人找不到重点，仓库也被撑大**。
- 只有数据没有结论：一屏表格读不出"到底过没过"。
- 另起一套配色（蓝色 hero）和项目其它文档放一起像两个项目。
- 用 Editor 的 FPS 直接承诺手机帧率。

## 8. 自检清单

- [ ] 文件名是 `中文标题_日期.html`，不是 `report.html`
- [ ] 顶层能直接看到报告，素材在子目录
- [ ] 结论把"能验收 / 不能验收"分开
- [ ] 每张表都有口径说明
- [ ] 有三张以上截图，动态效果有 GIF
- [ ] 截图是压缩过的网页尺寸，不是 3MB 原图
- [ ] 过程文件收进 zip，目录里没有散落的 markers / status
- [ ] 写了未验证项
- [ ] 所有链接都能打开（图片、zip、Markdown）
