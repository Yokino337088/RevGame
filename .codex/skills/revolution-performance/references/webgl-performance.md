# WebGL 定制性能优化

面向普通浏览器里的 Unity WebGL Player。先核对 Unity 版本、图形 API、浏览器与运行宿主。Editor 选中 WebGL 构建目标时仍跑在桌面上。浏览器的托管代码、后台工作和网络能力以实际版本为准，微信与抖音小游戏分别核对自己的适配和测试结果。 [Unity 2022.3 WebGL 技术限制](https://docs.unity3d.com/2022.3/Documentation/Manual/webgl-technical-overview.html)

## 先选需要测的阶段

| 玩家遇到的现象 | 优先量什么 |
| --- | --- |
| 刷新或第一次点面板后久等 | 真实点击到可见。分别量依赖请求、解包并取资源、实例装配、打开动画和首帧可画 |
| 第一发技能才顿一下 | 读条到可交互、真实首发效果，从浏览器调用记录核对 Shader 首次链接、字形准备与纹理更新 |
| 持续交火时偶尔卡住 | 真实帧间隔、游戏回调内外分段、绘制尺寸、工作量、GPU 有效样本和反馈等待 |
| 分帧后画面顺了，数字却久等 | 同时量入队到启动、实际准备并提交完成、每帧队列工作和整帧间隔 |
| 退场后内存逐次增高 | 同样的冷启动与多轮进出。记录加载峰值、退出稳态、池与资源所有权、有效内存计数 |

### 实包与控制变量

- 用目标 Unity 版本构建真实 WebGL Player 与同目标 AB（资源包），从 HTTP 或 HTTPS 正式入口运行。记录构建编号、资源版本、浏览器版本、显卡及图形后端、视口、DPR（设备像素比）、真实绘制尺寸、画质、前后台状态和刷新条件。着重核对网页实际使用的硬件后端。冷开固定网络延迟、带宽、缓存状态和交互时点。 [WebGL 构建与交付](../../revolution-framework/references/webgl-delivery.md)
- 先用原样重复复现，再做控制变量。可用同一个构建的测试开关做 A→B、B→A，固定随机种子、关卡、活棋数、攻击与技能次数、预热、采样起止点、画面和规则。必要时每轮使用独立但同配置的浏览器会话。冷启动、首次技能和稳态持续交火各有自己的窗口。保持满载到结尾，另外核对实际战斗事件和退场。
- 临时缩小绘制缓冲、停一组绘制或暂停飘字用于排除假设。恢复完整画面和正常规则后再验正式方案。先跑详细诊断定位，再用轻量探针保留帧间隔与业务指标复测。窗口内写预分配数值缓冲，截图、查询汇总、日志和排序放到窗口外。保留所有轮次、异常、实际时长和负结果。 [测量与归因](measurement.md)

### 计算帧间隔与回调耗时

- 开发测试包可用 [页内帧采样](../../revolution-framework/references/webgl-delivery.md#浏览器页内开发桥)。`frames.start` 和 `frames.stop` 成对调用，失败用 `frames.cancel`。先确认返回的 `valid` 和真实绘制次数，再读取帧间隔、回调内工作、回调间等待与首笔绘制前用时。只更新未绘制的回调留作计数，其耗时算入两张实绘画面之间的工作。慢帧的下一次申请标记以其直接前一回调为准。纹理调用数仅在详细模式启用。
- 用 `performance.now()` 等单调时钟记录**实际绘制回调进入时刻**。相邻两次的实际间隔可以拆成上一回调自进入到结束、其结束到下一次进入。分别记录第一条真实绘制调用、请求下一帧的时刻和可能存在的只更新未绘制的回调。用帧号或共同事件对齐 Unity 中的逻辑、反馈队列、浏览器调用和纹理更新。按采样口径标明记录的是回调还是实际绘制，独立记跳过绘制的更新。浏览器传入的 `requestAnimationFrame` 时间戳用于动画时基，实际代码进入、退出要实测。这里的浏览器间隔也与显示器实际呈现时刻各有口径。 [浏览器动画帧规范](https://html.spec.whatwg.org/multipage/imagebitmap-and-animations.html#animation-frames) · [Unity 单调实时时钟](https://docs.unity3d.com/2022.3/Documentation/ScriptReference/Time-realtimeSinceStartupAsDouble.html)
- 回调内部贵就继续拆规则、UI、字形、纹理上传调用、绘制提交和原生调用等待。上一回调结束前已申请下一帧、且确认中间无遗漏工作时，可以定位间隔主要落在回调之间。浏览器、系统、后台负载、驱动或 GPU 的具体份额，需要对应时间线或有效计时才能确定。纹理更新次数、其 JS 调用时间、GPU 用时和整帧间隔各自记录。 [浏览器性能时间线](https://developer.chrome.com/docs/devtools/performance/reference/)
- GPU 计时先检查目标浏览器支持，如果使用 `EXT_disjoint_timer_query_webgl2`，异步轮询结果可用性，并剔除 disjoint（计时失效）的样本。记录样本数和计时覆盖范围，例如整帧、某一笔背景绘制或新增深度 Pass（一次绘制操作）。缺计时填未测。 [Khronos WebGL GPU 计时扩展](https://registry.khronos.org/webgl/extensions/EXT_disjoint_timer_query_webgl2/)
- 一起报告实际窗口、平均 FPS（每秒帧数）、帧间隔 P95/P99、最大值、超过约定阈值的次数和交互等待。60 FPS 平均约 16.7 ms 每帧。阈值根据项目目标挑选，RevGame 的 25/50 ms 用来对照偶发波动。一个慢帧扣掉第 4 条起的飘字工作后低于线，只说明这段工作的量级，实际改动后仍需重跑调度。

## 点击前准备高频入口，AB 并发另量

1. 先让必要首屏、遮挡解除和正式互动条件完成。可选预热（玩家点开前先准备）只在当前域可交互、无遮挡、没有前台流程时发下一项。按入口命中率、首开可省的时间、额外传输与驻留成本决定小清单。同一域只启动一次，按优先级串行做候选并让出帧，前台点击继续沿正式打开路径。
2. 用 RevUI 元数据解析真正的面板逻辑路径和明确依赖的图集。RevScope（业务资源的持有范围）先登记具名租约再让帧，让冷启动、后台预热、前台打开通过同路径合并在途请求。正式界面仍等自身资源绑定完并可画。失败归还本次租约，退域清理未完成和已准备的资源。前台持有者有自己的引用，取消旧域前检查合用请求的所有权。 [资源与生命周期](resources-lifecycle.md)
3. 加载器内部可对独立依赖做少量有界重叠，实际 HTTP 传输另限全局。开始读目标资产前确认依赖成功。同代同包合用在途请求，在唤醒等候者前登记各自引用。批内失败等已发请求收尾再回滚实领引用，取消一个等候者留住其他持有者，退代中止旧传输与重试。分别核对 AB 版本、缓存键、发布 URL、冷缓存和热缓存命中。正式实现和并发配额以当前加载器为准。 [浏览器 AB 的冷开与依赖调度](../../revolution-framework/references/webgl-delivery.md#浏览器-ab-的冷开与依赖调度)
4. 用真实点击对照发请求数量、响应、装配与可见时刻。只能靠周期截图取样时，用最后一张未出现到第一张已出现作为区间，说明比较的是哪一端的统计量。将提前下载的体量、使用命中与额外驻留和省下的点击等待同时列出。

## 控制画布像素与真实过绘

- CSS 视口大小、设备 DPR 与 canvas 绘制缓冲是三个量。保留可见画面尺寸，缩放系数取 `min(DPR, sqrt(像素预算 / CSS面积))`，宽高分别向下取整，保证有效尺寸。Web 模板接管缓冲时协调 `matchWebGLToCanvasSize`，只在实际尺寸变化时重建。从浏览器画布和 Unity 实际分辨率读回结果，核对普通窗口、高 DPR、大小变化、全屏与同位置点击、落子。原生全屏沿实际用户手势请求。 [Unity WebGL Canvas 尺寸](https://docs.unity3d.com/2022.3/Documentation/Manual/webgl-canvas-size.html)
- 同一份 Wasm（浏览器运行的代码）切实际尺寸。短测核对设计取舍，持续负载核对波动与反馈。用 GPU 有效计时和画前/回调外耗时区分填充成本与其他问题。选择能兼顾画质和实际帧间隔的像素预算。
- 背景省绘使用真正被不透明棋盘格遮挡的范围。读取实际图集、切片内框与 alpha，软边和缝照常画。按目标渲染管线用合并网格在背景前写深度，验证相机、排序、演出移位时撤挂与重挂、退场释放。先证实同帧像素等价，再在开关两侧量同一范围的 GPU 总用时，将新增深度 Pass 算进去。覆盖面积、单笔 GPU 数据和整场帧率用不同指标说明。 [GPU 不透明覆盖方案](gpu-rendering.md#用真实不透明覆盖提前挡掉背景)

## 读条分批准备第一次交火

- 资源下载、对象池（暂存可重复使用的实例）和实际 Shader 变体（材质特定选项对应的画图程序）各有首次成本。浏览器时间线如果显示第一次技能在 `getProgramParameter` 等调用上等待链接，使用本章真正持有的材质、关键字与 Pass，在读条范围内提前准备。RevGame 从池实例和已就绪棋盘取真实材质，先准备弹道、近战、飘字、积分飞星和炸弹共用程序，再补裂隙、帮手弹幕与激光、落点。沿现有 `ShaderVariantCollection.WarmUp` 路径验证实际被使用的变体。 [Unity Shader 加载与预热](https://docs.unity3d.com/2022.3/Documentation/Manual/shader-loading.html)
- 每种准备前先用 RevTask 让出一帧。领取实例与材质后先记录所有权，再等待。取消、失败和离场按原租约收尾。测读条增加的耗时、首枚真实技能的等待、正常过场和后续稳态。只预热实际会使用的项目，按目标设备确认准备工作是否确实从战斗挪到了读条。
- 如果用动态字体，按正在使用的字体、字号与样式，选择常见字符分批调用 `RequestCharactersInTexture` 并让出帧。记录 `Font.textureRebuilt`、实际纹理更新和整帧时序。动态字形随后可能被换出，组合方案的整帧改善仍需单开关对照才能归因到预热。 [Unity 动态字形接口](https://docs.unity3d.com/2022.3/Documentation/ScriptReference/Font.RequestCharactersInTexture.html)

## 反馈队列按量和时间分帧

- 规则固定步先算完伤害、占格、计分。对已结算的显示事件持值快照，分别约束同屏数量、已预约的在途实例、每帧生成数、每帧软时间、等待上限和过期。按目标和伤害类型合并，保留首笔入队时间，用公平或最老优先的次序处理。动画、弹道和近战短效按独立的呈现预算，退出时按原代清理。
- 普通帧小额度，积压超过深度或最老一条超过年龄时可升到较大但有限的额度。预选一批最老记录，完成一条后再查实时时钟，余项留给下一帧。单次同步原生调用可能超过软额度，RevTask 的让帧只在可分割的操作之间生效。保住本批已经启动的文字，满屏时优先回收本批开始前的合适旧字，避免同帧创建又回收。 [UI 与反馈的通用契约](ui-feedback.md)
- 避让计算的累计代价已超过最优时提前退出候选，保持相同候选顺序和同分取舍。相机与现有文字在同一同步摆位批次内保持稳定时，可复用已算的屏幕占用矩形。键要包含批次与适用相机，当前字体重建、对象回池再借和文字或变换变化都要重新取值。异步续接、下一批、新帧或投影改变按实时状态查。测试同帧复用、重叠与轮换、字号变化、字体重建、相机和原排序。
- 计时分开写首笔命中入队到启动申请、入队到数字准备并交给引擎完成、浏览器两次实际绘制间隔。游戏时间和墙钟时间各按自己的单位比较。记录提交条数、显示覆盖命中数、丢弃与未出队量、最老等待和 P95/P99。几笔命中能合成一条显示，规则实伤与具体屏幕出现时刻另验。帧时改善和反馈更晚可能同时出现。
