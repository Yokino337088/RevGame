这台服务端管哪些事

想象两台手机各放了一颗棋，包到达的时间不同。两边要知道「这手属于谁、是否轮到他、落下以后对方应该看到什么」。服务端负责给这盘棋一个共同的房间、一份确认顺序和同一个规则结果。棋手掉线回来时，它还要认出原来的席位，并补上缺失的历史。

把人配成一局

Gate 接连接和匿名握手，按场次与规则匹配，分配黑白和一个 Battle。

把棋走成同一盘

Battle 用共享 GoCore 复核棋规。Gate 保存已确认棋谱并发给两席。

按同一个钟决斗

权威端确定资格、角色和帧顺序。两台设备用同一套原生规则重放。

服务器联机是九路围棋的一条入口。远征、无尽、本机人机、局域网对战分别有自己的流程。Unity 中的 Revolution 负责界面、场景和玩法生命周期，跨公网的会话与消息由 Fantasy 接管。服务端项目可以用 .NET 编译和运行，云主机只接收服务端产物。

玩家身份目前是匿名的恢复令牌和房间状态在内存中，同进程重连可以恢复。重启后要重新匹配。本机棋力参与匹配和计算本局增减分，当前用途是休闲分流。

为什么分 Main、Entity、Hotfix

截图里的三个目录各有一个 .csproj。编译后形成三个程序集，也就是三个 DLL。下面的箭头表示项目引用。例如 Hotfix 能读写 Entity 里的房间数据，Entity 只需定义数据及框架契约，Hotfix 的具体 Handler 由启动时加载。

目录这里负责什么改需求先去哪
Server/Main可执行入口。加载程序集，给 Fantasy 提供日志实现，启动进程。启动参数、启动异常和日志接线，读 Program.cs。
Server/Entity底层类型。房间、玩家、会话绑定、生成协议，以及从客户端工程链接进来的共享规则。这里直接引用 Fantasy-Net。给玩家增加会话字段或房间字段，读 Pvp/GoLobbyComponent.cs。启服拓扑看 Fantasy.config。
Server/Hotfix业务规则和消息入口。Handler 接请求，System 执行匹配、校验、状态推进和回收。修改匹配、落子和离场规则，先找 Hotfix/Pvp 的对应入口。

官方这样拆，是为了让数据与可换的逻辑有明确边界

例如调整匹配的分差策略，只要房间和玩家字段兼容，理论上可以只替换逻辑程序集。若数据类型和逻辑都在同一个待卸载程序集中，旧房间还持有旧类型，切换程序集就可能留下新旧类型以及生命周期问题。Fantasy 推荐拆层来支持热重载，也允许无需热重载的项目合并数据和逻辑。三层通常仍由同一个 Main 进程加载。真正启动几个进程、每个进程跑哪些 Scene，由配置和启动参数决定。

RevGame 的 AssemblyHelper 会把 Hotfix 的 DLL 和 PDB 从发布目录读入可卸载的 AssemblyLoadContext，触发编译生成的注册信息。仓库的运行入口在启动时调用它。本文采用「停旧版、启动对应版本、回归」的发布方式。在线热更需要另行验证定时器、在途请求、类型兼容和旧上下文引用的清理。

一台机器里为什么有五个 Scene

服务端的 Scene 是一个管理业务状态、调度任务和消息的容器。Gate 有大厅和玩家，GoBattle 有分配给自己的棋局。同一个棋盘由同一个 Battle 负责写入，其他 Scene 通过消息提交命令。不同棋局才有机会并行。

Machine / Process / World
Machine 描述一台机器和网络地址。Process 对应一组启动配置。World 是业务归属范围，可以挂同一组数据库配置。一个 Scene 同时归某个 Process 承载、归某个 World 管理。
Scene / Entity / Component / System
Gate 的玩家是 Entity，GoSessionComponent 挂到 Session 上保存当前玩家绑定，GoLobbyComponent 挂到根 Scene 上保存大厅索引。System 描述初始化、匹配和销毁行为，Scene 回收时会清理归属对象。
Session / RoomId / Address
Session 标识本次网络连接。RoomId 是业务房号，同一局两席共享。Address 是 Fantasy 的运行时路由地址，Gate 用它把命令送到那盘棋所属的 Battle。客户端只填 Gate 的 IP 和端口。
Root Scene / SubScene
当前五个都是配置创建的根场景，每个 GoBattle 下存多个房间对象。Fantasy 也支持按需创建 SubScene，用于需要独立生命周期的副本或地图，它共享父 Scene 的基础调度设施。RevGame 这版以房间数据表示一局棋。

五个 Scene 的 sceneRuntimeMode 都是 MultiThread，因此可以把围棋计算分给四个 Battle 线程。Gate 等待内网 RPC 时用 FTask，这是 Fantasy 的异步任务类型。这时 Gate 可以处理其它房间。等回包以后，要再核对房间和 Session 是否还是原来那一个。

从 .proto 定义到两端能读的消息

协议是一张双方约定的表。比如客户端希望在某个房间下一手棋，就提交 RoomId 和 Command。字段编号告诉解码器哪段字节对应哪一个字段。OpCode 用于识别是哪一种消息，和字段编号处于不同层。

GoRelay.proto · 项目现有落子请求 
message C2G_GoCommandRequest // IRequest,G2C_GoCommandResponse
{
    string RoomId = 1;
    GoRelayCommand Command = 2;
}
想做什么协议与 Handler本项目例子
向 Gate 问一件事Outer 的 IRequest / IResponse，接收端用 MessageRPC<请求, 响应>。登录式握手、匹配、落子和决斗交换。响应通过 RPC 对应到调用方。
Gate 主动通知玩家Outer 的 IMessage，发送端 session.Send(...)。G2C_GoState 是状态推送。当前 Unity 的接收类型是 Message<G2C_GoState>。
向已知 Battle 地址查询Inner 的 IAddressRequest / IAddressResponse，接收端用 AddressRPC<Scene, 请求, 响应>。Scene.Call(address, request) 批量校验同一 Battle 上的棋步。
通知 Battle 关房Inner 的 IAddressMessage，接收端用 Address<Scene, 消息>。G2B_CloseGoRoom 清理房间。发送方使用 Scene.Send(...)，无业务回包。

新增可选字段用新编号，保留现有字段的编号、含义和类型。改完源协议后运行 export-protocol.ps1，审查两处生成目录和 OpCode.Cache 的差异。生成的文件用导出器维护，项目代码实现 Handler 即可由 Fantasy 源生成器注册。外网契约不兼容时要协调客户端和 Gate，内网协议变化则需要 Gate 和 Battle 同版。

收包、发包和回包是三件什么事

Unity 侧拿到 Session 后，可以调用生成的 RPC 方法。RPC 指远程调用，调用方发送请求并等与它对应的回复。Fantasy 把对象编码成字节，填入数据长度、OpCode、本次 RpcId 等包头信息，交给传输层。UDP 负责传输数据报，KCP 在 UDP 之上做重传和排序。跨进程的内网这里用 TCP，框架负责从字节流中拼出一条完整消息。

RpcId、Sequence 和决斗 Frame 经常被误认为同一个数字。RpcId 用于找到这一次网络等待者，重试通常会有新的请求。Sequence 是围棋历史里第几条确认命令，重试时相同一手仍用同一序号。Frame 是决斗世界执行到的第几个逻辑步，和玩家本机的画面帧率分开。

普通 MessageRPC 在 Run 结束时由框架回包。正常写法是设置 response.ErrorCode 和相应字段后退出。需要明确提前发送时可以使用 reply()，发送后把响应视为已经交给框架。请求、响应和池化消息的引用只在当前处理期间使用。想长期保存完整棋谱或快照，可以把值复制到自己拥有的容器，或者按现成代码复制消息并在房间销毁时归还。

调试时可以顺着 连接 → 解码 → 当前 Scene 的 Handler → 业务状态 → 回包 看日志。两个客户端能建立连接，只说明传输层通了。RPC 收到响应还要看 ErrorCode。业务响应成功之后，再核对这些状态是否按序应用到玩家界面上。

为什么客户端还有一个接收 Handler落子 RPC 的回复给提交者，对手的状态通过 G2C_GoState 单向推送。Unity 的 G2C_GoStateHandler 把快照交给 FantasyGoTransport，玩法服务按序重放后，Revolution 的界面才看到新棋面。

Fantasy 消息与 RPC Handler · 包头定义 · Unity 推送入口

两个人怎样走进同一个房间

收到握手时，Gate 会核对 revgo-2、必需规则字段和格式，并给匿名身份返回一枚随机恢复令牌。GoSessionComponent 记录本条 Session 绑定了哪个玩家。下一次收到命令，服务端从这个组件找玩家和座位，再核对请求与当前房号。

匹配先用 MatchKind + RulesJson 分桶。同一组内，GoMatchPolicy 选择棋力距离最近的合格对手，距离相同优先队列里更早的人。按两人等待时间中较短的一方计算放宽窗口。等待未满 8 秒只接受同段至多 100 分差，8 至不足 16 秒允许差 1 段、200 分，16 秒起允许差 2 段、300 分。Gate 每秒重试和回收过期队列。开房时把当前负载较少的 Battle Address 写入房间，后面每手都沿这个地址走。

连上了，为什么一直匹配不到

先确保两个测试客户端都点了开始匹配，使用同一构建、同一个服务器地址、相同场次和相同规则。规则文本不同，等更久也只在各自队列里等。已有房间先离场。查服务端匹配日志，确认节点还有容量。

服务器对战面板 · 握手、匹配与房间 · 棋力距离算法

跟着一手棋读完整条链路

假设第 16 手已经确认，现在轮到黑方。黑方客户端先用同源棋规试算坐标，构造第 17 条操作。请求带着房号、行动方、操作类型、坐标、时间和前后局面指纹。前指纹告诉服务端黑方基于哪一个局面提交，后指纹告诉服务端黑方试算得到了什么。

  1. Gate 先挡住不属于这局的操作。 C2G_GoCommandRequestHandler 找到当前 Session 的玩家并限流，Relay 再查房间、座位、坐标、指纹和序号。每房最多一手等待 Battle，避免同一房的第 17 手没确认就提交第 18 手。
  2. Battle 独占棋盘。 Gate 按目标地址把多房间棋步合成最多 32 条的内网 RPC。凑满可立即发送，未满用 1 毫秒定时器给合批机会。Battle 把权威棋盘和完整劫历史填进本房间独占的草稿，使用 GoCore 校验。结果指纹也匹配才交换两块棋盘。校验失败时保留原权威棋盘，下一次仍能使用同一块草稿。
  3. 双方得到同一个已确认结果。 Gate 追加棋谱，向对手推送，再给下棋人回包。实际到达先后取决于两条连接。协商过增量同步时，在能衔接的情况下只带新的一手和基序号。首手的基序号为 0，握手、重连和主动同步使用完整棋谱。
  4. 客户端复核再落屏。 PvpService 检查序号和指纹，按顺序更新自己的棋盘。缺手时请求同步。收到网络回包与棋面通过本地回放是两步，排查时分别看。
同一手重发为什么不会多落一颗完全相同的旧序号重发可以返回已确认结果。同一序号携带不同棋步时会被拒绝。这样即使服务端上次已提交、客户端却没收到回包，双方仍能收敛到同一份棋谱。

当前联机围棋累计 68 手实际落子或连续双方停一手后，由共享规则直接计分。Gate 用 Battle 返回的终局裁决算两席本局增减分，客户端按房间号防止重复应用。这里的局面指纹用于一致性对账，联机身份、输入合法性、可信计时和持久化排名是各自独立的设计问题。

决斗为什么要封帧

围棋一手确认后才换人。决斗里，两个人在相近时刻可以同时按键。服务器给双方安排同一条逻辑时间线。玩家发的是方向和招式意图，权威端决定这些意图进入哪个完整帧，原生 RevGameCore 执行该帧，双方就能按相同顺序重放。

例如第 40 帧是双方都要对账的周期采样点。客户端收到连续的完整帧后用 DuelCorePipe 执行，再把自己的第 40 帧指纹报给服务器。权威侧用同一帧独立计算的指纹核对。确认同帧一致后，才向两席公布共同确认上界。缺历史的一端从自己的连续游标继续拉取，单包上限 64 帧。客户端的画面插值和即时预测是显示层的响应，命中与胜负以权威帧为准。

正常挑战最早从第 24 手开始，发起方的估算劣势至少 12 目。GoBattle 直接用已经确认的权威棋盘计算资格。它维护选角、加载和每席输入，同一 Battle 用一个计时器推进已双席 Ready 的房间。每次逻辑推进仍按 50 ms 固定步长。Release 联调从合法棋谱进入真实决斗，验收覆盖选角、双方加载、Ready、封帧与离场。

服务端部署时，原生 DLL 是决斗运行的一部分。围棋可以先连上，直到发起决斗才加载原生库。因此发布验证要点到真实决斗，才能发现缺 DLL、位数不符或规则版本不一致的问题。

断网、超时和退出后谁来收尾

Session 是这一次连接，玩家身份是 Gate 暂时保留的业务对象。手机切换网络导致旧 Session 断开时，匹配队列会移除该玩家。已有房间在配置的重连窗口内等他回来，并把断线状态通知对手。

新连接发带原令牌的 Hello。Gate 检查身份、规则和场次，解绑旧连接，把新 Session 接到原座位，再回完整棋谱。每次决斗席位换连接，Gate 通知 Battle 将该席的代际编号加一。Battle 清掉上条连接待封的意图，拒绝迟到的旧代际请求。新连接重新 Ready 后续原有历史。等待 Battle 回包期间若有人离席，Gate 会核对房间仍是原对象，再决定如何处理回包。

默认客户端约每 2 秒发业务心跳。配置的 Session 空闲阈值是 8 秒，检查间隔 5 秒，因此实际关闭取决于下次检查。棋局的重连窗口是另一项规则，项目配置一般为 90 秒。主动离席会关房通知对手、释放计算席位，两席都不再引用时回收房间。定时器和原生实例分别随负责它们的 Scene 与房间销毁。

当前房间和令牌的存活范围是原进程。即便预留 MongoDB、Redis 或 Control Center，也需要业务代码明确把哪些数据持久化、由谁恢复，否则重启后还是新对局。Fantasy.config 的 MongoDB 连接串在默认配置为空，当前联机路径依赖内存状态。

用一组数字理解怎么估带宽

示例假设 64 个活跃决斗席位各每秒收到 20 个回复，平均每个回复在网络上占 256 字节，其余出网共 0.50 Mbps。输入值示范算法，实际用同一时间窗口观测的发包次数和出网字节。

估算出网 3.12 Mbps，按 1.5 倍留余后为 4.68 Mbps。

算式为席位数 × 每席每秒回复数 × 单次平均字节数 × 8 ÷ 1,000,000 + 其它出网。ACK、KCP 重传、重连补历史和围棋推送会占用带宽，统计时每项只计一次。1.5 倍仅用于这个算例。部署后用腾讯云公网出带宽的峰值和 P99 验证余量。

从单台 CVM 走到跨进程 Battle

Fantasy 的拆分单位是可寻址、拥有状态的 Scene。一台机器可以有多个进程，一个进程可以承载多个 Scene。给围棋增加 Battle 时，Gate 只在创建房间时挑一个较空闲的节点，把它的 Address 记在房间。以后保持同一所有者。把活跃房直接切到另一台机器，还需要搬运状态、路由并处理在途请求。

原先跨进程压测时，第一批棋局会触发四条内网连接逐一创建。Fantasy 在 Windows 上为 TCP Socket 以 1 KiB 步长探测缓冲区。本机分段计时里，单条连接的初始化约 132–202 ms，回环握手低于 2 ms。当前 Gate 启动后先对四个远端 Battle 发就绪 RPC。RPC 确认组件已启动并建立缓存连接后，Gate 才将对应节点加入房间分配表。默认的同进程拓扑使用进程内路由。

上一轮 320 个真实 KCP 客户端压测中，预连接把首手 P99 从 845.16 ms 降到 62.24 ms。本轮在同一业务代码和同一探针下对比两个运行时。每个 320 人轮次包含 96 局围棋和 64 局决斗，所有对局均完成指纹核对与离场。

  1. 在同一个发布目录准备两条启动命令。Gate 和 Battle 共用同一版产物与同一份拓扑。

后台运行时为两个进程分别建任务和日志。停服更新时先停 Gate，让客户端不再进入旧版，再停 Battle。新版仍先启动 Battle，然后启动 Gate。要回退就同时切回同一套旧产物和拓扑，对应的运行时也要仍可用。

多台 Battle 仍可共用一个 Gate。以后若要多 Gate、自动故障接管，需要额外设计跨 Gate 匹配和重连路由、容量预留、房间恢复和重复请求处理。Fantasy Control Center 能做发现、注册和拓扑配置，Namespace / WorldGroup / World 用来组织服务与区服。注册到中心以后，房间、令牌与棋谱仍由业务保存和恢复。

$revXml = New-Object System.Xml.XmlNamespaceManager($revTopology.NameTable)
$revXml.AddNamespace('f', $revTopology.DocumentElement.NamespaceURI)
$revScenes = $revTopology.SelectSingleNode('//f:scenes', $revXml)
$revScene = $revScenes.SelectSingleNode('f:scene', $revXml)
