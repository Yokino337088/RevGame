为什么两台设备之间要有一台服务器

黑方在电脑上下了一手棋。白方手机要得到同一个结果。万一白方以为轮到自己、也同时点了一格，就由服务器查轮次，决定哪一手能记进棋谱。

如果两台设备上的局面不一样，就以服务器按规则确认的结果为准。代码里把这叫作服务端权威。决斗也一样。玩家告诉服务器「我按了跳跃」，负责这局的服务端代码会决定把这次按键放在哪一步执行，并算出结果。

Fantasy 是项目选用的 C# 服务端框架。它负责把消息送到正确的代码、管理连接和定时器。RevGame 自己写谁能排进同一局、哪里能落子、什么时候能挑战决斗。Unity 里的 Revolution 则支撑玩家看见的界面与游戏流程。

客户端对局服务 · 服务端消息入口

两个人怎样进同一盘棋

两位玩家都在游戏里填服务器地址。游戏连到服务端的入口。项目把这个入口叫 Gate。Gate 用一条记录代表此刻的网络连接，这条记录叫 Session。

GoBattle 就是代码里负责给棋局和决斗算结果的单元。Gate 会选当前分到的活跃棋局较少的一个。开好房间之后，Gate 负责告诉两位玩家对方是谁、自己执哪一色，并把后面的操作都交给这一个 GoBattle。

如果两个人都显示「正在匹配」，先确认他们都按了匹配，而且选的是同一个场次与规则。项目把场次和规则文本都相同的人放进同一组，再比较棋力差。

为什么有人等一会儿才配上

刚入队时要求同段，最多差 100 分。两人中等得较短的那位也满 8 秒后，允许差 1 段和 200 分。都满 16 秒后，允许差 2 段和 300 分。匹配会定时重新检查。这里的棋力用来安排休闲对手，客户端在本地保存积分。

一手棋怎样发出去，又怎样回来

假设这盘棋的房号是 R208，服务器已经收下前 16 手。现在轮到黑方。黑方点了坐标 (2, 3)，这次是第 17 手。

  1. 黑方先试算。 客户端用自己的棋盘试走这个格子，把房号、手数、坐标和落子前后的局面校验值发出去。校验值也叫 Hash（指纹），用来帮助两边确认此刻算的是同一个局面。
  2. Gate 查这是谁的请求。 它顺着 Session 找到黑方的座位，核对房号，确认轮到黑方，再交给这盘棋指定的 GoBattle。
  3. GoBattle 按自己的棋盘算一遍。 它用双方共用的 C# 棋规 GoCore 在草稿棋盘上试走。走法和算出的局面都对得上，才把草稿变成已确认棋盘。遇到非法落子或结果对不上，棋盘仍停在第 16 手。
  4. Gate 告诉双方结果。 Gate 记下这条棋谱，向白方发更新，再回复黑方。两条连接的速度可能不同，哪一端先看到取决于实际网络。
第 17 手已经下成，黑方没收到答复又发了一次，会下两颗吗？

Gate 会拿重发的第 17 手和棋谱对照。完全相同就按已确认的结果答复，棋谱还只有 17 手。如果把同一编号改成另一个坐标，Gate 会拒绝。缺了一手的客户端可以向 Gate 要完整棋谱补齐。

打开源码时先找哪几处

客户端在 FantasyGoTransport 调用 C2G_GoCommandRequest。Gate 从 C2G_GoCommandRequestHandler.Run 进入 lobby.Relay。Battle 在 G2B_GoBatchRequestHandler.ApplyStep 调用 GoCore。其它房间发给同一个 Battle 的棋步可合成一批，最多 32 手。每个房间同时只有一手在等确认。

断网换了一条连接，怎么还能坐回原位

第一次打招呼时，Gate 会回一段随机字符串，叫恢复令牌（ResumeToken）。游戏留着它。切换 Wi-Fi 时，原来的 Session 可能断开，但 Gate 还能在一段时间里记住「这个身份坐在这盘棋白方」。

默认给掉线的玩家 90 秒回到棋局。这段时间内暂停接收新棋步。测试时保留当前游戏和对局，短暂断开网络再恢复。过期或玩家主动离席时，大厅关房，并通知负责这局的 GoBattle 清理数据。Gate 进程重启会丢掉内存里的房间和令牌，玩家需要重新匹配。

为什么断网后有时过几秒才提示

平常客户端约每 2 秒发一次小消息，叫心跳。服务端按照配置检查空闲连接，每 5 秒检查一次，空闲超过 8 秒就会关闭。连接检查用来发现掉线，90 秒则是棋局发现断线后等人回来用的。

一台机器为什么能有五个 Scene

Scene 是 Fantasy 服务端里负责一部分工作的运行单元。每个 Scene 收自己的消息、按需启动计时器，并保管自己负责的数据。Gate 是一个负责接待玩家的 Scene，GoBattle 是负责算棋的 Scene。它们都在服务器上运行，游戏里的棋盘画面由 Unity 加载。

Machine 是在哪台电脑上跑
可以是你自己的电脑，也可以是一台腾讯云服务器。默认配置只写了 1 台。
Process 是这台电脑上跑着哪一份程序
敲一次启动命令就运行一份。默认只运行 Process 1，这一份程序内就有图里的五个 Scene。
World 是哪些 Scene 服务同一组玩家
可以把它理解成游戏的一个区。默认五个 Scene 都属于 World 1。Gate 只从同一个 World 里挑 GoBattle。即使把 Battle 移到另一个进程，它仍能属于这个 World。
Root Scene 是随服务启动的 Scene
配置里写了五条，所以启动时有五个。一个 GoBattle 能负责多盘棋。Fantasy 也支持运行时创建子 Scene，本项目的普通棋局直接存成房间数据。

可以把处理线程理解成程序里一条按顺序干活的队列。四个 GoBattle 各用一条，可以同时验不同房间的棋。同一盘棋始终只有一个 GoBattle 负责修改。比如这局分给 1003，下一手也交给 1003，因为这盘棋下到哪一步，只有它保存着完整的棋盘。

玩家的地址、内部地址和房号

IP:端口 给玩家找 Gate。RoomId 给游戏找一盘棋，例如示意房号 R208。Address 给框架找负责算棋的 Scene。Gate 从 R208 的房间记录中取出 WorkerAddress，把房号一并发过去。GoBattle 收到后按 R208 找到对应的棋盘。图里的 1003 是配置编号，发消息用的是框架提供的 Address。

同一个 GoBattle 能管十盘棋吗？

能。GoBattle 按 RoomId 保存多份棋盘。十盘棋分别有自己的记录，都可以由同一个 Scene 按顺序处理。Fantasy 的 Scene 关闭时会清理挂在它下面的对象，项目也会在单个房间结束后把那盘棋的资源清掉。

在 Fantasy.config 里怎样找到图中的 1003

搜 id="1003"。这一行的 sceneTypeString="GoBattle" 写明它负责算棋。processConfigId="1" 表示由第 1 份程序启动，worldConfigId="1" 表示给第 1 个游戏区服务。想把它搬到第二份程序，就改进程编号。给哪个区服务由 World 编号决定。

为什么代码分 Main、Entity 和 Hotfix

拿「玩家正在排队」这件事举例。Main 拉起服务器。Entity 定义服务器要记什么，例如玩家是谁、已经等了多久。Hotfix 写怎样找对手，例如根据双方等了多久决定允许多大的棋力差。

三个目录各有一个 .csproj，它告诉编译工具这个项目用哪些文件和依赖。编译以后会得到三个项目各自的 .dll，也就是装着编译后代码的文件。你只启动 Main.dll，它会把另两份代码一起加载。上节的一台机器和五个 Scene 是运行时怎么布置，三份 DLL 是源码怎么分工。

Fantasy 官方为什么推荐把数据和做法拆开

假如你只想改「等几秒才放宽匹配」，理想情况下可以保留原来的玩家和队列数据，换掉判断规则。这就是热重载，即让运行中的程序加载新版逻辑。Fantasy 建议把可替换的逻辑放进 Hotfix，把需要继续使用的数据类型放在 Entity。

在本项目，AssemblyHelper 在启动时加载 Hotfix.dll 和 Hotfix.pdb，让 Fantasy 找到处理消息的代码。实际上云换版时先停止旧进程，再从新目录启动整套文件。若要在不停服的情况下换代码，还得解决正在处理的请求和定时器怎么交接。

打开代码时，先分清谁记数据、谁做事

你会在 Fantasy 文档里看到 ECS，就是 Entity、Component、System 三个词的缩写。拿项目里的连接举例。握手成功后，Gate 要把「这条连接属于哪个玩家」记下来。

Handler 是消息刚到时先进入的那段代码。比如收到匹配请求，Handler 从 Session 找到玩家，再调用大厅的匹配方法。System 里写业务动作，也可以写创建、销毁时该做什么。Server/Entity 是存放数据类的目录名，代码里的 Entity 也是框架管理对象的类型。挂到 Session 的 Component 在 Fantasy 中也由框架当作 Entity 管理。Handler 和 System 通常放在 Server/Hotfix。

为什么我改了配置，服务器还是读旧的

平时编辑 Server/Entity/Fantasy.config，编译时会复制到输出目录。运行中的服务读 Main.dll 同一目录下的 Fantasy.config。若你重新起的是旧目录，就仍会看到旧端口。在云上部署，修改的是复制过去的那份配置。

直接运行 Main.dll 时，开发模式 --m Develop 会启动配置里的全部 Process。发布模式 --m Release --pid 1 只启动配置里编号 1 的一组 Scene。这里的 1 是配置编号，Windows 任务管理器显示的进程号由系统另外分配。

客户端和服务器约好了要传什么

黑方要告诉 Gate「我想在这盘棋的这个位置下一手」。两边事先约好要传哪些字段、每个字段是哪种数据，这份约定叫协议。本项目把约定写在扩展名为 .proto 的文本文件里。

GoRelay.proto · 实际的落子请求 
message C2G_GoCommandRequest // IRequest,G2C_GoCommandResponse
{
    string RoomId = 1;
    GoRelayCommand Command = 2;
}
  • C2G 表示客户端发给 Gate。这条消息的答复叫 G2C_GoCommandResponse。
  • RoomId 是房号，类型是字符串。Command 是这手棋的内容，里面还有手数、执棋方和坐标。
  • = 1 和 = 2 给两项数据编号。接收端读到编号 1 就按房号解释，已有的字段编号要保留。

Outer 是玩家与 Gate 之间的约定，例如「黑方请求落子」。Inner 是服务端内部的约定，例如「Gate 请 GoBattle 验棋」。玩家程序只需要 Outer。默认都在一个进程里时，Gate 和 GoBattle 仍按 Inner 的约定交换消息。

要加一个字段，应该改哪个文件

先改 Tools/NetworkProtocol/Outer/GoRelay.proto 或 Inner/InnerMessage.proto，再重新导出，由工具更新生成目录。新字段用未占用的编号。OpCode.Cache 保存整条消息的编号，避免重新导出时给已有消息换号。

生成消息代码与注册处理方法是两步。导出脚本给消息生成 C# 类。编译时，Fantasy 的源码生成器再把「收到这类消息时找哪个 Handler」准备好，启服会加载这份信息。

发送、回复、主动通知，各是什么

把 C# 里的房号、坐标等内容转成网络能传的字节，叫序列化。接收时转回程序里的数据，叫反序列化。Fantasy 完成这两步，再把消息交给对应的 Handler。开发者在 Handler 里从 request 取数据，在 response 填结果。典型请求在 Run 结束时由框架发回回复。

Gate 等 GoBattle 验棋时会遇到 await。它的意思是「这一手等答复再继续」。FTask 是 Fantasy 用来表示这种异步任务的类型。这个请求暂时等着，Gate 仍可以处理另一盘棋的消息。

看代码时，怎么认出一条消息属于哪类
玩家问，Gate 答
请求写 IRequest，应答写 IResponse，接收方法用 MessageRPC<请求, 应答>。
Gate 主动发给玩家
用 IMessage。例如 session.Send(...) 发送 G2C_GoState，Unity 的 G2C_GoStateHandler 接收。
Gate 问指定的 GoBattle
用 Scene.Call(address, request) 等答复，类型叫 IAddressRequest 和 IAddressResponse。只通知关房时用 Scene.Send(...)，无需等业务答复。
包头里的 RpcId 和棋谱里的 Sequence 是什么

包头是跟在消息内容前的一小段信息。OpCode 告诉 Fantasy 这是哪类消息，RpcId 告诉它回复应该交给哪个正在等待的调用。Sequence 放在棋谱里，表示这是这盘棋的第几条操作。黑方重发第 17 手时，网络调用可以换编号，Sequence 仍是 17。

网络传输也有约定。当前玩家消息用 UDP 传输，KCP 在上面处理重传和排序。Gate 与 GoBattle 分成两个进程后，内网消息走 TCP。同一个程序里的两个 Scene 由框架在进程内转交。

两个人同时按键，决斗按谁的顺序算

黑方按跳跃，白方按攻击，两条消息到达的时间可能不同。负责这局的 GoBattle 统一按每 50 毫秒一步推进。每一步叫逻辑帧。它描述游戏规则前进了一步，电脑或手机自己决定每秒把画面画多少次。

开始之前，挑战者必须符合围棋局面的条件。双方都选完角色、加载完，并分别发送 Ready（我这边已经准备好），服务器才开始推进。玩家从服务器知道这一帧该怎样演算，再用自己的游戏画面展示结果。

黑方已经看到第 39 帧，掉线回来要从第 1 帧开始吗？

客户端如果还有自己的第 39 帧状态，可以报 AfterFrame=39，意思是「从第 40 帧起发给我」。GoBattle 留着已经确定的帧历史。换连接会清除旧连接未执行的输入，新连接重新 Ready 后继续。第 40 帧等检查点，两端会把各自的指纹送回服务器比对。

挑战门槛和决斗核心在哪里

第一台腾讯云服务器怎么选

把服务端放到云上，就是租一台朋友能从别处访问的电脑，让它一直运行 RevGame 的服务端程序。腾讯云把这种电脑叫云服务器 CVM。

第一次小范围测试，先选这一档腾讯云 CVM 标准型 x86_64，4 vCPU、8 GB 内存、Windows Server 2022 64 位、80 GB SSD 云硬盘、5 Mbps 公网出带宽。有货可选 S6.LARGE8。选靠近多数测试玩家的地域，先按量试租。购买时确认实例会有公网 IPv4。

选 Windows 是因为仓库已经有对应的 Windows x64 决斗库，这条发布路径也做过本机验证。公网出带宽是服务器每秒能向玩家发多少数据。围棋下完一手才发更新，决斗会频繁发送新帧。5 Mbps 是小范围测试的起点，玩家多了要观察带宽和实际卡顿。

打算做什么起步配置看什么决定是否升级
两三个人验连接2 vCPU / 4 GB，50–80 GB 磁盘，3–5 Mbps先确认游戏可以配对、下棋和进入决斗。
首台测试服4 vCPU / 8 GB，80 GB 磁盘，5 Mbps 起让围棋和决斗同时跑一段，记录高峰使用量。
测试发现资源吃紧可试 8 vCPU / 16 GB，80–100 GB 磁盘，出带宽可测试 10–20 Mbps带宽常到上限就加带宽。某个线程持续吃满就再看是 Gate 还是 Battle 在忙。

价格以当时控制台为准。下单前看清主机、Windows 镜像、磁盘和公网网络各自怎么计费。短期、流量少的测试可以比较按流量计费，长期稳定流量再和固定带宽比价。

想估一下带宽，试着改决斗人数

每秒向这些玩家发多少数据

下面先假设 64 位玩家在决斗，每位每秒收到 20 次回复，每次 256 字节。其它围棋、心跳等流量合计 0.50 Mbps。把人数加倍，可以直接看到估算怎样变化。这些输入是教学用的数字，上云后用自己的监控数据替换。

估算出网 3.12 Mbps，按 1.5 倍留余后为 4.68 Mbps。

人数 × 每秒次数 × 字节数 × 8 ÷ 1,000,000，再加其它出网。乘 8 是把字节换成比特。最后乘 1.5 是这个例子留出的余量。监控时把补历史、重传和其它回复的流量也算进去。

IP 告诉玩家要连哪台机器，端口告诉它找这台机器的哪个程序。比如 203.0.113.10:20000 的前半段是 IP，后半段是端口。文档用的是示例 IP，实际换成腾讯云控制台显示的公网 IPv4。

腾讯云 Windows · 修改发布目录的 machine 节点 
<machine id="1" outerIP="203.0.113.10" outerBindIP="0.0.0.0" innerBindIP="127.0.0.1" />
outerIP · 告诉别人用哪个地址
填腾讯云的公网 IPv4。玩家也在游戏里手动填这个 IP 和端口。
outerBindIP · 本机在哪些网卡上接玩家的包

innerBindIP · 在哪个本机地址等内部消息
Gate 与 Battle 都在这台电脑时填 127.0.0.1，内网监听只允许这台机器自己访问。

什么时候才需要把 Gate 和 Battle 分开跑

第一次部署用默认配置，启动一份程序就能配对、下棋、决斗。以后要给 Battle 单独分配计算资源，可以把这四个 Scene 移到第二份程序。两个程序可以先在同一台电脑上跑。

分开跑之后，Gate 得先确认负责算棋的那份程序能接消息。现在 Gate 在分配房间前就会问每个 GoBattle「准备好了吗」。收到答复后，再让房间使用这条已建立的连接。以前等到玩家第一手才连，前几手就会一起卡在建连接上。

我需要同机双进程，具体怎样改
  1. 从同一版服务端的发布目录开始，两份程序使用同一份 Fantasy.config。
  2. 在原有 <processes> 内加一条 Process 2。Gate 1001 的 processConfigId 仍为 1，把 1002–1005 的 processConfigId 都改为 2。保留 World 1 和各端口。
  3. 第一个窗口运行 dotnet Main.dll --m Release --pid 2，看到 SceneCount:4。第二个窗口运行 dotnet Main.dll --m Release --pid 1，看到 SceneCount:1 和四条「Battle 内网就绪」。最后用两个客户端实际配房。
Fantasy.config · 放进原有的 processes 节点 
<process id="2" namespaceId="1" machineId="1" startupGroup="0" />

同一台服务器上，内网地址继续用 127.0.0.1。移到两台机器时才需要各写一条 Machine，让对应 Process 指向那台机器。内网填写同 VPC 的私网 IP，只向必要的内网来源放行 TCP。更新双进程时先停 Gate，再停 Battle。启动新版仍先 Battle 再 Gate。

Fantasy 文档里还会看到哪些词
Control Center / ServiceDiscovery
Control Center 记录各服务器和 Scene 怎样布置。ServiceDiscovery 是程序用来查询在线实例的功能。比如有一批战斗节点会随时开关，Gate 可以问「现在有哪些在线」。当前 RevGame 的节点在配置文件里列好，Control Center 默认关闭。
Namespace / WorldGroup
用 Namespace 可以把测试服和正式服的服务清单分开。WorldGroup 可以把几个游戏区归在一组，例如把「华东一区、华东二区」都放到华东组。RevGame 分配 Battle 时看的是 Gate 所在的 World。
Address
已经知道找哪一个 GoBattle，就用 Address 把消息点对点送过去。RevGame 的落子和决斗都使用它。
Roaming
假设一款游戏允许玩家换地图，每张地图由不同 Scene 管。Roaming 可以维护玩家当前绑在哪个地图服务，框架就能把从 Gate 收到的漫游消息自动送到那里。
SphereEvent
假设棋赛结束后，统计和通知服务都关心结果。它们可以各自订阅同一事件，发布结果的一方只发一次事件，由框架通知订阅者。
SubScene
有些游戏会为临时副本创建一个子 Scene，副本结束就销毁。RevGame 的围棋房间用一份房间记录和棋盘表示，多个房间都可以由同一个 GoBattle 管。

以后如果增加多个 Gate，仍要决定房间和重连信息谁保存、节点故障时怎么恢复。Control Center 提供查询在线节点的能力，保存对局进度仍是游戏业务的工作。

P99 可以这样看。在 100 次落子中，把响应时间由快到慢排好，第 99 次所用的时间就是这个例子里的 P99。越大代表靠近最慢的那批操作等得越久。「首手」从每个房间取第一条操作，「稳态」看已经开始后的操作。

上一轮同机双进程的 320 人测试中，开局前连好 Battle 后，首手 P99 从 845.16 ms 降到 62.24 ms。分开计时以后发现，慢在系统创建连接时准备发送和接收数据的空间，每条连接约花 132–202 ms。真正让两边连上的时间低于 2 ms。

手上只有一台电脑，怎样用工具模拟两位玩家

GoRelayProbe 是仓库自带的联机测试工具，它会创建两条真实的 KCP 连接，匹配、下棋并挑战决斗。先在一个窗口起本地服务端，确认 KCP 20000 在监听。接着在另一个窗口从仓库根目录运行下面两个代码块。第一个为探针编译独立目录，并把探针自己的内网端口设成 11102。端口被占用就换一个空闲端口。

从仓库根执行 · 为 KCP 探针准备独立配置 
Set-Location .\RevGame_Server\RevGame.Server
$revProbeDir = Join-Path $env:TEMP ('RevGame-Probe-' + (Get-Date -Format 'yyyyMMdd-HHmmss'))
dotnet build .\Tools\GoRelayProbe\GoRelayProbe.csproj -c Release -o $revProbeDir
if ($LASTEXITCODE -ne 0) { throw '探针编译失败，请看构建日志。' }
$revProbeConfig = Join-Path $revProbeDir 'Fantasy.config'
[xml]$revTopology = Get-Content -LiteralPath $revProbeConfig -Raw
$revXml = New-Object System.Xml.XmlNamespaceManager($revTopology.NameTable)
$revXml.AddNamespace('f', $revTopology.DocumentElement.NamespaceURI)
$revScenes = $revTopology.SelectSingleNode('//f:scenes', $revXml)
$revScene = $revScenes.SelectSingleNode('f:scene', $revXml)
foreach ($revWorker in @($revScenes.SelectNodes('f:scene[position() > 1]', $revXml)))
{
    [void]$revScenes.RemoveChild($revWorker)
}
$revScene.SetAttribute('outerPort', '0')
$revScene.SetAttribute('networkProtocol', '')
$revScene.SetAttribute('innerPort', '11102')
$revMachine = $revTopology.SelectSingleNode('//f:machine', $revXml)
$revMachine.SetAttribute('innerBindIP', '127.0.0.1')
$revTopology.Save($revProbeConfig)
在探针准备的同一 PowerShell 窗口 · 两席围棋和决斗 
Set-Location -LiteralPath $revProbeDir
$env:REVGO_LOAD_ENDPOINT = '127.0.0.1:20000'
$env:REVGO_DUEL_PROBE = '1'
try
{
    dotnet .\GoRelayProbe.dll --m Develop
    if ($LASTEXITCODE -ne 0) { throw '探针失败，请看输出。' }
}
finally
{
    Remove-Item Env:REVGO_DUEL_PROBE, Env:REVGO_LOAD_ENDPOINT
}

见到 GO_KCP_DUEL_PASS 时，看报告的棋步数、帧号和双方指纹。结束后用 Ctrl+C 停止你为本次测试启动的服务端。
