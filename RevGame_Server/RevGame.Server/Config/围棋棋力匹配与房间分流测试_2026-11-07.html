匹配与房间归属

玩家从同一个 KCP Gate 进入，按场次和规则分组。在同组内先比段差，再比分差，距离相同时优先等待更久的人。窗口按双方较短的等待时间，在 8 秒、16 秒放宽，分别允许 1、2 段差与最多 200、300 分差。两人一旦配成，Gate 选当前房间数最少的 Battle 根场景并固定该局的 Address。该线程校验棋规并管理实盘，Gate 负责棋谱下发和恢复。

新身份从 1500 分开始，双方确认数子或本人认输后更新棋力。Unity 在同一次游戏运行中复用同地址、同昵称、同规则的匿名令牌。服务端短期档案最多 4096 条，最后一次计分后有效 30 分钟。

i7-12700H，14 核 20 线程。探针先分批登录并保活，再同时发起匹配。每轮 500 局各走 30 手，再执行双停与两次计分确认，共 17,000 条操作。探针核对双方棋谱与哈希、满载重连、离席和回大厅。服务端日志核对每局的分配、结算和释放地址一致，每轮均有 500 次棋力更新。

批次匹配耗时从开始并发匹配算起，单手延迟为同机客户端请求到收到回包的往返时间，包含网络、排队、棋规与快照。三轮共用本机的运行负载不同，特别是第三轮同时执行了编辑器和其他本机回归。尾延迟在该条件下明显波动。这些数据验证功能容量，公网延迟和长期稳定性仍需线上环境验证。千人压测使用的构建早于内部 RPC 响应归还的修订，最终版再通过 20 人 KCP 和下列定向回归。

Unity 自动化调用

  1. rev_discover(editor, editor.status) 确认目标编辑器。rev_call(editor.status / editor.refresh / editor.compilation) 等待新程序集，编译诊断无错误。
  2. 编译后 rev_discover(editor, editor.play)。rev_call(scene.list / editor.play / runtime.start) 从 Assets/Scenes/StartScene.unity 进入 Play。rev_discover(game, pvp.) 找到 41 项真实业务能力。
  3. rev_run 分两段。第一段调用 pvp.enter / pvp.connect / pvp.match / pvp.kcp-opponent 组成真实 KCP 房间。第二段等到当前座位执棋，提交认输、回大厅并重新连接，对照服务端棋力记录和运行时日志。两段断言均通过。
  4. 最后执行计划清理及 rev_call(editor.stop)。该回归走 game 业务能力，没有调用 GM 目标。身份验证以服务器和业务断言为证据，未做视觉采样。

早先两次尝试分别遇到 Play 等待超时、旧程序集和对手停手指令竞争。最终复测使用刷新后的程序集，并在轮到验收玩家时提交认输。

框架与部署边界

Fantasy MultiThread Root Scene 与 Address RPC 可支撑同一进程内的房间分流。Gate 仍集中处理连接、排队和棋谱下发。当前结果覆盖单机单进程。跨机容灾、账号级长期段位和公网延迟属于另外的验证范围。
