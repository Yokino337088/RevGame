围棋服务端千人匹配与并发压测

2026-11-07 · Fantasy.Net 2026.1.2003 · Windows x64 · i7-12700H · Release · 真实 KCP 回环

结果

三个千人场景均形成 500 个双人房，每局提交 30 手落子和 4 次数子操作。全部 17,000 条命令在对应房间校验序号及结果指纹，服务端各记录了 500 局同源规则审计结果，错误日志为零。满载时换 Socket 能恢复原身份、房间和棋谱，双方离席后回到 idle。

基线取自 cc7d4e4 的服务端源码。同一百桶负载下，命令回复和对手推送合计由 892,500 条棋谱记录降至 595,000 条，减少 33.3%。计数是实收记录条数。延迟是探针在回环链路上观察到的端到端命令 RPC，包含探针调度和服务器日志开销。

并发输入和断言

  • 探针在同一机器独立进程运行，按批建连登录并保活，所有 1,000 个已登录会话就绪后一次发起匹配。每个局内命令波次同时提交 500 条 RPC，间隔约 90 ms，并穿插业务心跳。
  • 百桶测试包含相同规则但不同场次、相同场次但不同规则。每间房恰有两个不同执色的客户端，且场次与规则一致。另跑了同规则的千人突发。
  • 匹配前验证重复请求仍在等待、取消后回到 idle。数子结束后核对对手推送。以原令牌换真实 KCP Socket 后读取原房间和 34 条棋谱。全部离席并主动同步确认状态为空。
  • 小批量以 20 个真实 KCP 客户端验证探针连通，形成 10 局，执行 100 条操作。压测首次卡在客户端批量创建 Socket 的缓冲区探测，改成建连分批并保活后，匹配测量仍从全员就绪开始。
  • 原有 TCP 探针回归通过，覆盖冒用执色、相同操作重发、同序号改写、重放指纹和重连离席。

实现与容量边界

在原有 Fantasy Gate Scene 线程内，以场次和完整规则作为键管理 FIFO 链表。排队、取消和断线摘队直接访问对应桶或节点。单局仍由独立房间 Entity 持有棋谱。已有响应覆盖的落子者、当前匹配请求者和重连者不重复收同一份推送。棋谱、协议和重连入口保持原契约。

这个结果验证了当前主机上的单 Gate、KCP、500 局突发负载。现有 1,024 份匿名身份上限也计入重连保留身份。公网延迟、生产硬件、持续时长和多进程故障恢复需要各自的压测。Root Scene 可按配置独立调度。更大的共享匹配池需要独立的配对所有者、通过 Address 路由的多个房间所有者和可恢复的归属目录。Fantasy Scene 文档

服务端和探针 Release 编译通过。服务端保留了基线中共享 GoCore 的 7 条可空性警告。探针独立于生产服务，为使用锁定版本 Net 包内的真实 KCP，探针进程一次绑定客户端工厂并接收已导出的协议响应。生产大厅继续使用框架正常 Handler 注册和 FTask。源码和启动方法见 部署配置说明。
